# Repository working conventions

## What this is

mimicry is a Go HTTP client that reproduces real browsers' network fingerprints. Accuracy first, then speed. The library module is the repo root (`github.com/roachadam/mimicry`); `harness/` is a separate module that captures real browsers and diffs mimicry's profiles against them.

## Commands

Tool versions are pinned in `.prototools` (Go, moon). golangci-lint is pinned in `.moon/tasks/go.yml` and run with `go run`, so it is built with the pinned Go; run it through moon rather than a system install.

```sh
moon run :test :vet :lint   # every project
moon run mimicry:test       # the library only
moon run harness:test       # the harness only
```

`:test` runs `go test -race ./...`. Its inputs are the Go sources and the data the tests read (`testdata` directories, `profiles/data`; the harness's also the library's sources and profiles), so moon replays a cached result only when none of them changed.

## Package boundaries

The public surface is small: the root package (`Transport`, `NewClient`, `Config`, `HeaderOrderKey`, `Place` and `ErrPlacement` (header placement), `ErrNotMeasured`, request kinds: `Kind`, `Request`, `As`, `With`, `Exact`, and `CORSError`; `ProxyError`; certificates: `Pin`, `PinError`, `FetchPins`, `CertPin`, `CertRole`; WebSockets: `Transport.DialWebSocket`, `WebSocket`, `WebSocketOptions`, `MessageType`, `CloseError`), `cookies` (the jar; `cookies.New` returns `(*Jar, error)`; `Transport.Cookies` returns a Transport's), `profile` and `profiles`; `cmd/pins` prints a site's pins. Everything else is in `internal/`, flat, one package per concern. Each package's `doc.go` states what it may import; keep to it.

- Only `internal/handshake` and `internal/quic` (QUIC's TLS, decision 0027) import `github.com/roachadam/utls`.
- Only `internal/engine/native` assembles the request path (pool → dial → handshake → h1/h2, or QUIC → h3).
- `profile` imports the standard library only.
- Public packages never import from `harness/`.
- Use `net/http` types in the public API. Header order comes from the profile (the navigation, or the request's kind and its variant), with `HeaderOrderKey` as a per-request override and `Config.HeaderPlacement`/`Request.HeaderPlacement` moving single headers within the profile's order (decision 0030); pseudo-header order comes from the profile only. Do not fork `net/http`.
- One dial path (`internal/dial`), and every network step honours the context and its deadline.
- Never hold a lock across network I/O.
- Configuration is a struct (`Config`), not functional options or boolean parameters.

## The uTLS fork

mimicry depends on `github.com/roachadam/utls` at a pseudo-version of its `main` branch. To move to a newer fork commit, merge it there and run `go get github.com/roachadam/utls@main`. To try an unmerged fork change, use a local `go.work` that includes `../utls`; it is gitignored and must never be committed.

## Go clocks in tests

Use `github.com/jonboulle/clockwork` for code that depends on the current time. Inject a `clockwork.Clock`, use `clockwork.NewRealClock` in production and `clockwork.NewFakeClockAt` in tests. Advance the fake clock instead of sleeping.

## Go formatting

Write Go function and method bodies on multiple lines, including simple accessors and test stubs. Do not use one-line declarations such as `func (p *Profile) Name() string { return p.name }`.

Write struct declarations and populated struct literals on multiple lines, with each field on its own line and the closing brace on a separate line. This includes single-field structs, constructor return values, and structs passed as function arguments. Empty `struct{}` types and empty literals may stay compact.

```go
type Plan struct {
    hello *utls.ClientHelloSpec
}

cfg := mimicry.Config{
    Profile:     profiles.Chrome155MacOS(),
    DialTimeout: 30 * time.Second,
}
```

## Tests

Use the standard `testing` package with hand-written fakes; no assertion libraries. Tests must be deterministic: inject randomness and clocks rather than depending on them.

Prefer e2e and integration tests: a behaviour browsers show belongs in an e2e replay of its capture, not in a unit test that restates the rule. Write a unit or raw-peer test only for what no capture can reach, and only when the failure would be serious: a crash, a deadlock or stall, a security bug (injection, smuggling, leaked credentials), a hostile server, or an error path (`ErrNotMeasured`, refused requests). One table test per such area, not one test per case. Before deleting or skipping a unit test because e2e covers it, break the code and check that an e2e test fails.

Profile accuracy is proven by the harness against real browser captures, not by unit tests that restate a profile's values. `harness/e2e` checks every built-in profile against its browser's captures:

- `TestProfilesMatchCaptures`: mimicry's request to the capture server has no differences from the browser's capture (TLS, HTTP/2 preface and first request, headers).
- `TestHPACKReproducesBrowserBlocks`: re-encoding the browser's traced requests with the profile's `http2.hpack` reproduces every header block byte for byte, in every sample of every scenario and on every connection of every replayed real page. `http2.hpack` cannot be captured; this is what keeps it honest. A failure names the first instruction that differs.
- `TestConnectionMatchesBrowserTrace`: on one connection, mimicry's first header block and largest upload DATA frame match every sample of the browser's trace, and every WINDOW_UPDATE credit increment it sends lies within the range the browser's own increments span (± one frame). Ranges, not single values, because credit timing varies between a browser's own connections.
- `TestCookiesMatchBrowserTrace`: cookies set by the server come back from mimicry, through its cookie jar, in the browser's order and HPACK representation.
- `TestKindsMatchBrowserTraces`: every request of the kinds page (over HTTP/2, HTTP/1.1 and plain HTTP, the last with the page's navigation too) and its CORS preflights, made through mimicry as its kind from its page: header lines (names, order, values), HTTP/2 weight, which requests share a connection, and cookies as the browser sent them. Where the browser's own samples differ, any form it sent passes and the variance is logged. The only other tolerances are pinned tables: `raceCookieLabels` (a label whose browser sample lacks a cookie mimicry already holds, one direction only) and `partitionGaps` (Firefox's known connection differences, label by label); any other difference fails, and so does a listed gap that no longer appears.
- `TestCookiesScenarioMatchesBrowser`: every probe of the cookies page, made through mimicry from its page, has the browser's full header lines and HTTP/2 weight, and so its cookies in its order.
- `TestCookiesEdgeMatchesBrowser`, `TestCookiesEdge2MatchesBrowser`: every step of the cookies-edge and cookies-edge2 pages, walked through mimicry as the browser walked them (navigations and same-origin fetches, `http://` steps over plain HTTP where the browser used it, cookies-edge2's on its plain-only second port), sends each sample's Cookie header exactly: prefixes, nameless cookies, order, SameSite across schemes, loopback, the per-site limit.
- `TestCORSMatchesBrowser`: the cors page's fetches through mimicry send the browser's preflights and requests, connection by connection and in order: when a preflight is sent or cached (Max-Age, the 5 s default, replace or merge), no request after a refused preflight (a `*CORSError`), a redirect's second preflight.
- `TestCORSEdgeMatchesBrowser`: the cors-edge page's fetches through mimicry follow redirects as the browser did, connection by connection and in order (method, path, body length, Origin): no next request after a cross-site redirect without `Access-Control-Allow-Origin` (a redirect's `*CORSError`), PUT/DELETE keeping method and body on 301/302, GET on 303 and for POST (Safari keeps its Origin: `redirects.method_change_origin`), 20 redirects at most.
- `TestRedirects2MatchesBrowser`: the redirects2 page through mimicry, step by step (markup images, new Image(), XHR, crossorigin img/script, fetch() with PUT/POST/HEAD/PATCH and credentials, form POSTs, the 25-redirect navigation), sends every request the browser did, connection by connection, with its header lines and weight: CORS check on every CORS-mode redirect, 307/308 keeping bodies, Firefox's and Safari's preflight of a preflighted PATCH's GET hop (`redirects.hop_preflight`), the navigation limit (`redirects.navigation_limit`: Chrome 19). Listed gaps: navigations to another site compared apart from their connection (no top-level-site partition), Chrome's error-page reload, layout-driven image priorities, Firefox's `www.redir-c.test` connections. `TestNavRedirectsMatchBrowser`: the four typed navigations whose start URL redirects (within the origin, apex to www, to another site, http to https) through mimicry, request for request; and the navigations of nav-redirect-page (by script and form, redirected to another origin: same-origin and same-site URLs to another site, www to static and apex to www, another site back to the page's, a form GET and a form POST answered 303), nav-redirect-form (form POSTs by script answered 301 to 308 between every pair of relations; `Origin: null` on a 307/308 by `redirects.navigation_origin`) and nav-redirect-click (the same forms and links clicked: `Sec-Fetch-User` on every hop), made from the page as redirects2's are, a click's with `Sec-Fetch-User` and a script's without. Safari 26's clicks were never captured (`missingCaptures`).
- `TestResumptionMatchesBrowser`: on the resume page, mimicry opens and resumes as many connections per host as the browser did, and every resumed ClientHello has no differences from the browser's.
- `TestConnectionsMatchBrowser`: the connections page through mimicry opens the browser's connections (hosts, protocols, requests per connection, Chrome's preconnect pinned as the one known difference), coalesces the same hosts onto the same HTTP/2 connections (Firefox's declined connections included), and spreads the 10 parallel HTTP/1.1 requests over 6 connections as the browser does.
- `TestProxyMatchesBrowser`: through the capture proxy, mimicry's CONNECT lines, SOCKS5 bytes, credential flow (challenge first or every time, retry on the same connection, unasked when the browser does) and forwarded plain-HTTP requests (line for line) are the browser's, and the tunnelled ClientHello is the profile's. A missing capture fails unless `missingCaptures` lists it (Safari 26's two proxy-credential captures and both Safaris' `proxy-websocket-auth`, never taken); a listed one that exists fails too. `TestUnmeasuredProxyIsAnError`: any proxy for a profile without a `proxy` section, credentials without `connect_auth`, and a WebSocket through a proxy without `proxy.websocket`, with credentials where `proxy.websocket.credentials` is unset (Safari), or `ws://` through SOCKS5, are errors.
- `TestHTTP1MatchesBrowserTrace`: over HTTP/1.1, mimicry's two navigations are the browser's header lines exactly, casing, order and values, in every sample of the `http1` scenario (authority normalised): `/` as a typed URL, then `/nav` sent through mimicry as a navigation from the page, with the page's cookies from the profile's own jar. Only `Sec-Fetch-User` is suppressed (the page navigates by script, without user activation).
- `TestWebSocketsMatchBrowser`: every socket of the `websocket` and `websocket-h2` pages, and of the `proxy-websocket`, `proxy-websocket-auth` and `proxy-websocket-socks5` pages through the capture proxy, opened through mimicry from its page as the browser walked them, against every sample: transport (an HTTP/1.1 connection of its own with the browser's TLS hello, or an extended CONNECT stream on the connection that carried the page's request to the host), what reached the proxy for it (the CONNECT lines, status and credentials or SOCKS5 bytes of its tunnel, the page's own for a stream, or nothing for a handshake sent whole), handshake (header lines verbatim; HTTP/2 fields, pseudo-header order, HEADERS flags, priority, stream WINDOW_UPDATE), every client frame (FIN, RSV, opcode, mask, length form, payload, compressed bytes included: varied text of every size, empty and incompressible messages, `client_no_context_takeover`, `client_max_window_bits` 8 to 15), the pong, HTTP/2 DATA packing (frames that fit one DATA exactly; larger ones within the cap, header alone where the browser's is), close frames, and who ends the transport, how and how soon after the last frame. A ws:// socket from the https:// page is refused before anything is sent; a socket the browser fails after its handshake (Safari's 8-bit window) fails to open, its transport ended as the browser's; a step the page skips in a browser it hangs (Firefox's 8-bit window) must fail to open. `TestDeflateReproducesBrowserMessages` replays every captured message through the profile's compressor (`ws.Compressor`) and names the first differing byte. Listed variance: Chrome fragments its 70 KiB message in some samples (mimicry never does); mimicry's cross-site stream shares the cross-site host's own connection (no top-level-site partition, logged).
- `TestHTTP3MatchesBrowser`: the `h3-discovery` and `h3-page` pages walked through mimicry from their pages as the browser walked them, pauses and the 35 s idle included (about a minute; the eight profile × scenario subtests run in parallel), against every sample (Chrome's and Firefox's `-h3-local-roots` captures, Safari's unforced): each request's transport (HTTP/2 or HTTP/3, which connection of its host, 0-RTT), whether a host's first QUIC connection started with its TCP one (Firefox's switch on Alt-Svc), the HTTP/2 connections the browser sent GOAWAY on, and per QUIC connection its first flight (what it sent before its first ACK or its first probe, the first datagram repeating CRYPTO or STREAM data or a lone PING, so a loaded machine's late server leaves probes out: datagram sizes, padding, packets, header bytes, token), ClientHello (`diff.Compare`), transport parameters, 0-RTT packets and NEW_CONNECTION_IDs (retransmissions counted once), credit frames and close, its unidirectional streams, SETTINGS, control frames, every QPACK instruction, and per request its header list, field lines, frames, PRIORITY_UPDATE and end. Features the samples agree on must match; ones they differ on are logged; numbers lie within the samples' range. What a browser draws per connection (packet numbers, DCID length, the CRYPTO cuts with their PINGs and padding, a cut's unusable last byte included, transport parameter order, GREASE and ECH lengths, `initial_rtt`, ACK delays, the spin bit, Safari's request after HANDSHAKE_DONE) or does by timing (whether its reply to the server's Initial carries a padded 1-RTT packet: each datagram with an Initial packet is held to where the profile pads it instead) is never compared with the samples' few draws: `quicRuleViolations` (`http3_rules_test.go`) holds mimicry's connections to the rule the profile states, the `rules` subtest holds every connection of the browser's h3 captures to the same rule (a rule the browser contradicts fails), and `compareDraws` fails a draw repeated on every connection of a page. Known differences are pinned in `h3Gaps` (a pinned gap that stops appearing fails).
- `TestHTTP3EdgeMatchesBrowser`: the `h3-blackhole`, `h3-broken`, `h3-vn` and `h3-v2` pages (the last where python3 has aioquic) through mimicry on the browser's schedule (each step at its time, whatever the earlier ones take; the 16 profile × scenario subtests run in parallel, about 75 s), against every sample: each request's connections in order and its delay; per QUIC attempt whether it resumed, its versions, what the server answered, how it ended, its datagrams and give-up time where the server never answered, when it started after its trigger and after the host's TCP connection; per TCP connection its trigger, the race against the QUIC attempt and the GOAWAY sent; the hello and transport parameters of a connection retried after Version Negotiation (Firefox's own hello). A connection that moves to a new path (Chrome) sends the browser's number of probes first and moves `quic.loss.path_degrading.after_ptos` of its own PTOs (measured from those probes, no shorter than RFC 9002 allows on the trace's RTT samples) after its last request, within half a PTO; every browser sample is held to the same rule, so it holds under `-race` and load. Times lie within the samples' range widened by `edgeSlack`; known differences are pinned in `h3EdgeGaps`.
- `TestHTTP3DownloadMatchesBrowser`: the `h3-download` page through mimicry: during the 50 MiB response the client never starts a key update and follows every one of the server's, acknowledges every `quic.ack.every` packets (Chrome: exactly 10 in at least 95% of its ACKs) or at least that many where the profile batches (98%), sends no ACK_FREQUENCY or IMMEDIATE_ACK, with every browser sample held to the same rules; each of its MAX_STREAM_DATA increases, and of its MAX_DATA ones where the profile raises it by a share of the connection window (Chrome, Firefox), lies within the range of the browser's own (± `creditSlack`, one packet: a client counts consumption in the steps its packets arrived in, so where the share falls inside the crossing packet is chance). Where the connection limit follows what arrived (`connection_stream_window`, Safari) the increases are timing, so the rule is checked on mimicry and every browser sample alike, against what the client's ACKs acknowledged (server data packets less the connection's mean overhead, the recorder not opening their payloads; the estimate's error is bounded by the bytes those packets carried beyond the least overhead, 4.6–5.8 KB, plus a packet): no MAX_DATA runs ahead of what the next ACK acknowledged by more than the stream window (grown where the client's MAX_STREAM_DATA ran further, Safari 26's first sample), and the median raise is at least what was acknowledged by then plus the window (Safari 27 sends a quarter to a third of its limits from older counts). The requests after the download go on its connection. The ACK shares, how far a batching client's ACKs advance on average (machine timing, not checked) and the credit ranges are logged.
- `TestQPACKReproducesBrowserSections`: re-encoding every browser's HTTP/3 field lists with the profile's `http3.qpack` reproduces every field section and encoder stream instruction byte for byte, on every connection of every h3 capture.
- `TestQUICInterop`: every profile against quic-go's HTTP/3 server through a seeded relay (`harness/internal/udprelay`), one table of rows run in parallel (about 20 s): handshake, 10 MB download, 2 MB upload, concurrent streams, Retry, resumption and 0-RTT accepted and rejected (where the profile resumes), ChaCha20 (a child process with AES off), server key update, the anti-amplification limit, loss, corruption and blackholes in the handshake and in transfers, a small MTU, port and address rebinding, GOAWAY, idle and server closes, stream resets, tiny flow control windows. Every response is checked byte for byte and every row against its time limit. Rows that impair the handshake hold a profile whose browser drops its QUIC attempt when TCP connects (Safari) to that race instead: an attempt that needs a probe loses, every request goes over TCP within the race, and the origin is given up after `broken_after` attempts. It is the one table for QUIC failures no capture reaches; a fix there adds a row that fails without it.

Behaviour that depends on time (Chrome's 5 s credit return, its idle PING) is tested in `internal/h2` with a fake clock against a raw HTTP/2 peer; the captures show it, the unit tests pin it.

## Built-in profiles

Built-in profiles are JSON files in `profiles/data/`, one per browser version and platform; the accessor functions (`profiles.Chrome155MacOS()` and the rest, each returning a fresh copy) are generated from them by `cmd/profilegen`. Every built-in profile must pass `profile.Parse`, enforced twice: the generator refuses to generate from an invalid file, and a test in `profiles` parses every embedded file. A profile without a matching capture in `harness/testdata/captures/` is not finished.

`profile.Parse` is `profile.Decode` (strict JSON: unknown, miscased and repeated keys are errors) followed by `Validate`. Captures record one connection and are not complete profiles, so the harness loads them with `profile.Decode`.

Each profile file is complete and self-contained: no inheritance between versions or platforms, so every value is visible in one file and checked against that version's own capture. A new version starts as a copy of the previous one; replace every captured field from the new capture, and treat everything copied that a capture cannot show (`http2.hpack`, header slots, `cookies`, `http1` slots) as unverified until the e2e tests pass against the new traces. Planned: `profilegen derive` to automate this copy and list the copied fields.

`profiles/EVIDENCE.md` lists every claim the profiles make, its evidence (wire, fitted to the wire, measured on another request kind, or copied) and the test that keeps it true. A profile change that adds, removes or re-sources a claim updates its row in the same commit.

A profile's `kinds`, `context` and navigation `variants` are generated, never hand-edited: `go run ./cmd/kindsgen -profile ../profiles/data/<name>.json` (in `harness/`) derives them from these captures, and refuses captures it cannot reconcile:

- `<name>.kinds.pagetrace.json.gz` and `<name>.kinds-http1.pagetrace.json.gz`: every kind over HTTP/2 and HTTP/1.1, and the context rules;
- `<name>.kinds-plain.pagetrace.json.gz`: the non-secure variants;
- `<name>.cors.pagetrace.json.gz`: `context.preflight_cache`, and the cors page's fetches, merged into the Fetch kind (its PUT variants, and cross-site fetches with and without a header the page set: the `page_set` condition);
- `<name>.cookies.pagetrace.json.gz`: the cross-site form POST navigation variant (`c-nav-post.so`), the image and injected_image `{same-site, redirected, cross_origin_redirect}` variants, and slots its requests add (Safari 27's `cookie` on a redirected same-origin image);
- `<name>.cors-edge.pagetrace.json.gz`: fetch redirects merged into the Fetch kind (PUT/DELETE hops, the GET hops of 303s and POSTs, a same-origin chain, a cross-site hop within its origin); every redirect's request takes its `cross_origin_redirect`, `origin_before_redirect`, `method_changed_by_redirect` and `insecure_before_redirect` conditions from the captured request it follows;
- `<name>.redirects2.pagetrace.json.gz`: redirects of every kind (`redir-<kind>`: images, crossorigin scripts, XHR, fetch() methods and their PATCH preflights, form POSTs and the navigation chain; Chrome's error-page reload left out);
- `<name>.nav-redirect-*.pagetrace.json.gz` (any number, optional): navigations whose start URL `/p/<label>` redirects to `/p/<label>.hop<n>`, over HTTP/2 or plain HTTP/1.1: typed ones (no Referer; their requests take `site: none`) and a page's (`nav-redirect-page`, `nav-redirect-form`, `nav-redirect-click`; the label's sites). A clicked navigation (`nav-redirect-click`) is grouped with the script's of its condition, so its variant gains the `sec-fetch-user` slot; their orders must merge. A request one sample sent in a form no condition explains (browser state) is left out only if pinned in `sampleGaps` with why, and a pinned one missing from its capture is an error;
- `<name>.headers-order.pagetrace.json.gz`: `context.header_table`, and fetch/XHR requests with headers the page set;
- `<name>.websocket.pagetrace.json.gz` and `<name>.websocket-h2.pagetrace.json.gz`: the `websocket` kind (handshakes over HTTP/1.1 and as HTTP/2 extended CONNECTs, whose `:protocol` must follow `http2.pseudo_header_order`, and `ws://` from the plain page as its `insecure` variant). `hellogen` derives `tls.websocket_h1` from the first;
- `<name>.h3-discovery*.pagetrace.json.gz` and `<name>.h3-page*.pagetrace.json.gz` (unforced and `.local-roots`): `http3.headers` (each kind's HTTP/3 list against its HTTP/2 one: Firefox's pseudo-header order, dropped `te`, `alt-used` placement), `http3.high`/`http3.low` (priorities measured only over HTTP/3), the `kinds.xhr` POST variant, and Safari's `injected_image.low` from its `h3-page` requests over HTTP/2; a layout-driven priority is pinned in `h3PriorityGaps`.

The QUIC and HTTP/3 sections come from the same h3 captures. Run the three generators in this order, each with `-profile ../profiles/data/<name>.json` (in `harness/`), each refusing a sample its rule does not describe: `go run ./cmd/hellogen` (it also writes `tls.quic`, the QUIC ClientHello, from every h3 connection's hello, and `tls.quic.version_negotiation`, Firefox's other hello after Version Negotiation, from the `h3-vn` captures), `go run ./cmd/h3gen` (`quic`, and `http3` but for kindsgen's header lists and priorities; it checks every value against every connection and pins the few samples that differ in `sampleGaps`), then `go run ./cmd/kindsgen`. hellogen and h3gen read the edge captures too (`server.H3EdgeCaptures`: `h3-blackhole`, `h3-broken`, `h3-vn`, `h3-download`), from which h3gen derives `quic.loss` (probes, give-ups, abandon closes, path degrading), `quic.keep_alive`, `quic.ack`, `quic.credit`, `quic.key_update`, `quic.version_negotiation` and `http3.discovery.fallback`; kindsgen reads only `h3-discovery` and `h3-page` (`server.H3ProfileCaptures`). Each has its own `TestRegenerateReproducesProfiles`, which fails while a committed profile differs from what it derives. A profile file with these sections is regenerated, never hand-edited; `go generate ./profiles` refreshes the accessors afterwards.

A variant only the cors, cors-edge or cookies capture shows was measured over HTTP/2 only, so it has no `http1` list, and mimicry refuses such a request over HTTP/1.1 (`ErrNotMeasured`). Rerun kindsgen after recapturing any of these; `TestRegenerateReproducesProfiles` (in `cmd/kindsgen`) fails while a committed profile differs from what kindsgen derives from the committed captures, and `TestKindsMatchBrowserTraces` checks the result against the same traces.

## Documentation

`docs/` holds working documentation (see `docs/README.md`). A change that makes, changes or reverses a design decision adds or updates its record in `docs/decisions/` in the same commit (copy `template.md`, next number, add it to the index). A feature that lands updates its concept doc in `docs/concepts/`. Write the reasoning while it is fresh: the options rejected and the evidence matter more than polish.

What gets modelled follows decision 0029: a behaviour an anti-bot vendor plausibly checks, or one a user would notice (a stall, a failure). Every known gap and deferred item is in `docs/backlog.md`, with its detection relevance and what closing it takes. A gap found or pinned (a new `sampleGaps`-style entry, a known-gap row in `profiles/EVIDENCE.md`) is added there in the same commit; a gap closed is removed. Automatic wire behaviour beyond the caller's own requests is listed in `docs/concepts/what-mimicry-does.md` with the option that changes it; a new one is added there.

## Capturing browsers

`moon run harness:capture` launches every installed browser (Chrome, Firefox, Safari) against an in-process capture server and writes new captures to `harness/testdata/captures/`. It never overwrites; delete a capture to retake it. Use visible windows for captures you commit: headless Chrome reports `HeadlessChrome` in its user agent. moon skips this task when `CI=true`.

Each browser is sampled three times (`-samples`), each on a fresh server and port so no connection or TLS session carries over. If the samples differ only in extension order, the capture records `"extension_order": "shuffled"` (Chrome), otherwise `"fixed"`. Any other difference between samples fails the capture: it is randomness a profile cannot describe and needs investigating.

The capture page loads like a site: a stylesheet, an image and a script on one connection, then a 16 MiB download, a 200 KB upload, a request carrying a header whose Huffman coding is longer than its value, and a navigation to `/nav` with two cookies (scoped to `/nav` and deleted there, so Safari keeps nothing). The page ends by requesting `/done`; an HTTP/2 connection that ends before that is a truncated trace and is skipped, logged with its last frames. `<name>.h2trace.json` is a JSON array with every sample's trace: every frame the browser sent and each header block's HPACK instructions. The profile JSON still comes from the first request only.

Scenarios (`internal/server/scenario.go`, `-scenarios`, default all but replays) capture the same browser under other server behaviour: server-set cookies, unusual SETTINGS, a slow download, an idle connection, and HTTP/1.1 only. Each writes `<name>.<scenario>.h2trace.json`; its first request is compared with the default page's and any change is logged as a finding. The `http1` scenario offers only `http/1.1` in ALPN and writes `<name>.http1.h1trace.json` instead: per sample, every request of the page load across the browser's connections, request line and header lines verbatim, with the connection each came on. The HTTP/1.1 recorder rejects a line that does not end in CRLF instead of recording it as if it did. Add a scenario when a behaviour might depend on the server; reuse the default page wherever possible.

Replay scenarios load the shape of real pages with synthetic content, to check what the small capture page cannot: hundreds of requests of every kind, dozens of hosts and connections, kilobytes of cookies. Record a page with a throwaway Chrome profile (`--log-net-log=FILE --net-log-capture-mode=IncludeSensitive`, 5 s on `about:blank` first, as the capture tool does), then `go run ./cmd/pageshape -site nike.com -out testdata/pages/nike.com.json FILE` (in `harness/`); delete the log afterwards, it holds real cookies. Only lengths and character classes leave it. `-scenarios replay-<site>` replays one page, `replay` all of `testdata/pages` (not part of the default run: each sample takes the page's length, up to 35 s). Each host is served under `.test` with its site kept apart (`www.nike.com` → `www.nike-com.test`, `server.ReplayHost`) and its own certificate from the capture CA; generated documents (top and every iframe's) schedule the recorded requests with the element or API giving their `sec-fetch-dest` and mode; cookies of the recorded shapes are set and deleted again at the end. The capture is `<name>.replay-<site>.pagetrace.json.gz` (gzipped: tens of MiB of JSON otherwise): per sample, every HTTP/2 connection's trace (with its host) and every HTTP/1.1 request. Its profile keeps only the ClientHello and user agent, since the first request on the connection that ends the page varies with timing. HTTP/3 parts of a real page are replayed over HTTP/2.

Chrome starts on `about:blank` and gets the capture URL 5 s later: a fresh profile rebuilds its certificate verifiers within seconds of launch and retires every open connection, which a long-running browser never shows a server.

`go run ./cmd/tracestat FILE.h2trace.json...` (in `harness/`) lists the features a capture's samples disagree on (request order, HPACK shapes, priorities, frame order exactly; largest DATA frame and median WINDOW_UPDATE within 2%). A varying feature is either modelled or recorded as a known gap; never pick one sample's value.

`go run ./cmd/diff WANT.json GOT.json` (in `harness/`) lists every difference in what a single-connection capture records (the ClientHello, the HTTP/2 preface and the first request's headers), comparing extension order as WANT's `extension_order` says, and exits 1 if there are any. The rest of a profile (`http1`, kinds, variants, context, cookies, proxy, hpack, flow control) is not compared.

`go run ./cmd/clientcapture -scenario NAME -out DIR -name LABEL -- COMMAND {url}...` (in `harness/`) captures any other client: it runs the command three times, each against a fresh server, keeps each run's first connection that carried a request, and writes the combined capture (logging, not failing, when the client varies where browsers do not). `reports/` holds comparisons made with it; date them, name the client versions, and keep the captures in `testdata/clients/`.

`go run ./cmd/interop -local` or `-public` (in `harness/`; opt-in, never part of `go test`) runs every profile's QUIC and HTTP/3 against other implementations: `-local` starts the QUIC interop runner's server images in Docker standalone (handshake, transfer, multiplexing, Retry, resumption, 0-RTT, ChaCha20, key update, loss, corruption, blackholes, discovery, blocked UDP); `-public` goes to real HTTP/3 sites with ordinary homepage GETs (Alt-Svc discovery through the public API, then a fresh and a resumed QUIC connection). `-servers`, `-cases`, `-sites` and `-profiles` narrow a run; `-addr PORT -setup DIR` reruns the cases against a container started by hand. Results go to `harness/reports/quic-interop-<date>.md`.

`go run ./cmd/realcheck` (in `harness/`; opt-in, never part of `go test`; needs the network) compares mimicry with the real browsers as public fingerprinting services see them: every profile visits echo endpoints (tls.peet.ws, tls.browserleaks.com, fp.impersonate.pro over HTTP/2 and HTTP/3) as a navigation, then a few homepages behind bot-management vendors (Cloudflare, Akamai, DataDome, HUMAN, Amazon) once each, a few seconds apart, with Go's net/http client last for contrast. `-browsers chrome,firefox,safari` drives the installed browsers through the same visits first; this **takes over the screen** (Chrome and Firefox on throwaway profiles over DevTools and WebDriver BiDi, Safari in a new window of the user's own, through AppleScript), so keep it to one short batch. Answers go to `-out` (default `$TMPDIR/mimicry-realcheck`; it holds this machine's public IP, never commit it), and each run compares everything there, field by field, into `compare.md` and `compare-full.md`: a browser `browser-<name>-<major>` against the profile `<name>-<major>-macos`, with per-connection randomness the profile models (shuffled extension and transport parameter order, GREASE ECH lengths and suites, random packet numbers) told apart from differences. `-echo=false -sites=false -profiles none` only compares. Results go to `harness/reports/realcheck-<date>.md`.

- Chrome and Firefox run with throwaway profiles (no extensions, default settings) and resolve the capture hosts to 127.0.0.1 themselves; Chrome ignores certificate errors and Firefox gets a certificate exception (or, for pages across several hosts, trusts the system's roots). Nothing on the system changes.
- Safari cannot be isolated: it opens a tab in the user's own window (closed afterwards). It must have **no content blocker or other extension enabled** while capturing (they block requests and strip cookies) and default privacy settings. It resolves through the system, so the capture tool runs a DNS stub answering `*.test` with 127.0.0.1 (`internal/dnsstub`), reached through `/etc/resolver/test` (created once: `sudo mkdir -p /etc/resolver && printf 'nameserver 127.0.0.1\nport 15353\n' | sudo tee /etc/resolver/test`). Capture names are under `.test`, never `.localhost`: WebKit treats every `*.localhost` host as a site of its own, which turns same-site requests cross-site. Safari must also trust the capture CA. The CA lives in `<user config dir>/mimicry/capture-ca/`, outside the repo, and is name-constrained to `test` and `localhost` with IP addresses excluded, so it cannot vouch for any real site. Trust it once; the capture command prints this when needed:

  ```sh
  security add-trusted-cert -r trustRoot -p ssl -k ~/Library/Keychains/login.keychain-db \
    ~/Library/Application\ Support/mimicry/capture-ca/ca.pem
  ```

  To undo: `security remove-trusted-cert` with the same file, then delete the directory.
- The click scenario (`nav-redirect-click`) has the tool click as a user does, so each navigation has user activation (`Sec-Fetch-User`; a script's `click()` has none): a page waiting for a click takes the title `mimicry-click` and fills its window with its link or submit button, and the tool clicks its middle once per URL (again after 6 s if it is still there). Chrome is clicked over the DevTools protocol (`Input.dispatchMouseEvent`) and Firefox over WebDriver BiDi (`input.performActions`, with `remote.prefs.recommended` off), both on their throwaway profiles. Safari is clicked through the system's mouse events (`CGEventPost`, after its window is brought to the front), which needs Accessibility access for the app running the tool; an ssh session has none, so the second Mac cannot take this scenario. The mouse moves to Safari's window: leave the machine alone while it runs.
- Proxy scenarios (`proxy-*`) put the capture proxy (`harness/internal/proxy`: HTTP CONNECT, absolute-form, SOCKS5, all recorded) in front of the server; a scenario with a plain port gets what goes to that port (tunnels and absolute-form requests) on the server's plain side, as if the proxy had connected there, and each connection the server records carries the proxy connection it came through (`capture.WebSocket.ProxyConn`). Chrome gets `--proxy-server`, Firefox proxy prefs. With credentials (`proxy-auth`, `proxy-plain-auth`, `proxy-websocket-auth`) the tool answers the browser's 407 over Chrome's DevTools protocol (browser-level `Fetch`) and Firefox's WebDriver BiDi (with `remote.prefs.recommended` off, so the remote agent changes no networking prefs), as a user typing into the login dialog. Safari takes its proxy from the system: point the active network service at the tool's PAC script once, which proxies only `*.test`, and turn it off after (the first run after setting it may time out while Safari fetches the script; run again; on these Macs `networksetup` changed it without `sudo`):

  ```sh
  sudo networksetup -setautoproxyurl <service> http://127.0.0.1:15356/mimicry.pac
  sudo networksetup -setautoproxystate <service> off
  ```

  The tool also accepts manual web and secure web proxies at `127.0.0.1:15354` instead of the script; it then passes every non-`*.test` request through to the network unrecorded, since the whole Mac uses the proxy, and the Mac has no working proxy between samples or after the run until the proxies are turned off. Manual proxies send everything to the HTTP proxy, so with them the tool skips Safari's SOCKS5 scenarios (logged, and Safari counts as failed); those need the PAC script. For Safari's credential flow (`proxy-auth`, `proxy-plain-auth`) macOS itself must hold the credentials: install a `com.apple.proxy.http.global` device profile (manual proxy at `127.0.0.1:15354`, `ProxyUsername`/`ProxyPassword`, `PayloadScope: System`), then type the credentials into the proxy login dialog macOS raises; saving them in System Settings, `networksetup` or the keychain was not enough (see `harness/reports/proxies-2026-10-24.md`). Remove the profile afterwards.
- HTTP/3 scenarios (`h3-discovery`, `h3-page`) also serve QUIC on the TLS port's UDP twin and advertise it with `Alt-Svc: h3=":<port>"; ma=86400` on every response; the browser discovers HTTP/3 itself (decision 0026). The page's capture adds `quic`: each QUIC connection's datagrams with every coalesced packet's header and frames (the recorder, `internal/quictrace`, decrypts them: Initial keys from the client's first Destination Connection ID, Handshake and 1-RTT keys from the server's TLS key log, 0-RTT keys from the resumed ticket's PSK), its ClientHello and transport parameters, its HTTP/3 streams, frames and QPACK instructions, and how it closed; TCP connections carry `ms` (when their ClientHello arrived) on the same clock, so a race shows. Chrome and Firefox refuse QUIC with a certificate that does not chain to a built-in root: by default the capture records the attempt. `-h3-local-roots` lifts the refusal (Chrome: `--origin-to-force-quic-on` with the page's hosts on unused port 1, which forces nothing the page visits; Firefox: `network.http.http3.disable_when_third_party_roots_found=false`), records it in the page's `conditions` and names the capture `<name>.<scenario>.local-roots.pagetrace.json.gz`. Chrome also ignores Alt-Svc unless the certificate verified, so it needs the capture CA trusted by the system, as Safari does (the tool warns).
- HTTP/3 failure, version and transfer scenarios: `h3-blackhole` (Alt-Svc names a UDP port that records every datagram and answers none), `h3-broken` (HTTP/3 works, then one connection goes silent mid-request, then the server closes another and answers no QUIC connection started after that), `h3-vn` (quic-go speaking only version 2, so a version 1 Initial gets Version Negotiation), `h3-v2` (aioquic behind the server's UDP socket, which relays and records both directions; aioquic upgrades a client that lists version 2 compatibly, RFC 9368) and `h3-download` (a 50 MiB incompressible response over HTTP/3, then small requests: credit, ACKs, key updates). `h3-v2` needs `python3` with aioquic (`pip install aioquic`; the script is embedded, `internal/server/aioquic_h3.py`; its connections have no `h3` record); without it the tool skips the scenario and exits non-zero. The steps start on a fixed schedule whatever the browser takes (`H3Step.NoWait`; each URL carries `?t=`, the script's `performance.now()`), the pages' HTTP/2 traces carry `ms` on the datagrams' clock, and every QUIC connection also records the server's datagrams (`server`: Initial and Handshake packets opened, Version Negotiation versions, Retry integrity checked, 1-RTT headers unmasked), its transport parameters, and datagrams from another client port (`path`, a migration). Chrome and Firefox need `-h3-local-roots` for all but `h3-blackhole` (no certificate ever arrives). hellogen and h3gen read all but `h3-v2` (`server.H3EdgeCaptures`); `TestHTTP3EdgeMatchesBrowser` and `TestHTTP3DownloadMatchesBrowser` replay them. Results: `reports/http3-edge-2026-10-25.md`.
