## Fairness notes

- **Protocol checks.** Every measured response is checked against the protocol under test using the server's own view (its `x-proto` header: `$server_protocol` in nginx, `r.Proto` in the Go server). A load point with a single response on another protocol is discarded with the reason, as is a micro benchmark (it prints no result). Before measuring, each client is warmed up until three responses in a row come over the protocol.
- **How each protocol is reached.** HTTP/1.1 is tested on each server's http/1.1-only port (ALPN offers nothing else, no Alt-Svc) for every client, plus the client's own switch where it has one (tls-client `WithForceHttp1`, httpcloak `WithForceHTTP1`, azuretls `ForceHTTP1`, net/http `Protocols`). HTTP/2: mimicry `Config.DisableHTTP3`, httpcloak `WithForceHTTP2`, tls-client `WithDisableHttp3`, net/http `Protocols`, azuretls ALPN with HTTP/3 never enabled. HTTP/3: net/http's baseline is quic-go's `http3.Transport`; httpcloak `WithForceHTTP3`; azuretls `EnableHTTP3` + `ForceHTTP3`; tls-client has no HTTP/3-only switch, so `WithProtocolRacing` (QUIC against TCP per host, winner kept); **mimicry has no switch either: it moves to HTTP/3 after the server's Alt-Svc, as Chrome does**, so it is warmed up onto HTTP/3 and a fresh Transport can never start on it (layer 2 `handshake=full` over HTTP/3 is n/a for mimicry).
- **Certificates.** Every client verifies the servers against the benchmark's CA; no client skips verification in any scenario. azuretls's HTTP/3 transport ignores its TLS configuration hook, so it trusts the CA through the system roots (`SSL_CERT_FILE` points at the CA in the client container); the others get it as a pool.
- **Bodies.** Each client is used through its ordinary request API: net/http, mimicry and tls-client stream the body (drained into `io.Discard`); httpcloak's `Session.Do` and azuretls's `Session.Do` return it fully buffered, so their allocations grow with the body (10 MB per request at the largest size).
- **Headers.** mimicry sends its Chrome profile's headers for the request's kind: the micro and load scenarios' requests are `Fetch` calls from a page on the same origin (no CORS preflight), page loads are a navigation and element kinds. httpcloak sends its preset's headers. tls-client and azuretls get a fixed set of Chrome's navigation headers, in Chrome's order, as their users pass them. net/http sends Go's few default headers. Request sizes therefore differ by a few hundred bytes; HPACK/QPACK make that small on a warm connection.
- **Profiles.** Each client's newest Chrome: mimicry `chrome-156-macos`, httpcloak `chrome-latest` (155), tls-client `Chrome_152_PSK` (the variant of 152 that resumes TLS sessions as Chrome does; plain `Chrome_152` keeps no session cache), azuretls `chrome` (its spec says Chrome 133).
- **Resumption (layer 2).** `handshake=resumed` closes the client's connections between requests and keeps its session cache; a request counts only if the server says it resumed (`x-tls-resumed`). net/http is given a TLS session cache, as a caller who wants resumption sets one. azuretls keeps no session cache by default, so it never resumes (n/a). mimicry over HTTP/3 resumes with 0-RTT, as Chrome does.
- **Connection pools.** net/http and tls-client get `MaxIdleConnsPerHost` 1024 (their default of 2 would close and reopen connections at every concurrency above 2); the others keep their defaults.
- **The server is not the bottleneck.** Each server has its own CPU set (more cores than the client); its CPU use is read from its cgroup over each window, shown in the tables, and a point where it passes 90% is discarded. Both servers allow 1000 concurrent streams on HTTP/2 and HTTP/3, and nginx keeps connections for 10 million requests.
- **CPU and memory are per process.** Each load point, idle-memory measurement and page-load set runs in a worker process of its own, so heaps, goroutines and GC never mix between clients. CPU per request is the process's user+system time over the window divided by the requests completed in it; it includes the load generator's few goroutines, the same for every client.
- **This machine.** A laptop: Docker runs in a VM, the CPU sets are the VM's CPUs (which of the host's performance and efficiency cores serve them is up to macOS), and other load on the Mac shows up as noise. Short windows (see Environment) trade precision for time; compare clients within a table rather than across runs.

### Browser-faithful by design

Where mimicry is slower because it does what Chrome does, the tables mark it ‡:

- **HTTP/1.1, more than 6 concurrent requests:** mimicry opens at most 6 HTTP/1.1 connections per host (the profile's `connections.http1PerHost`, Chrome's limit) and queues the rest, first come first served; the other clients open one connection per concurrent request. Its requests/s and latency at 16, 64 and 256 measure the queue. `Config.MaxConnsPerHost` raises the limit, at the cost of looking unlike a browser (`mimicry-conns16` and `mimicry-conns64` when run).
- **Page loads over HTTP/1.1:** the same limit, per host: 31 requests over 3 hosts go out at most 6 at a time per host.
- **Page loads over HTTP/2:** mimicry coalesces www, static and api onto one connection (one certificate covers them and they resolve to one address), as Chrome does; the others open one per host. Fewer handshakes, all streams sharing one TCP congestion window: faster on a clean network, slower under loss. `Config.DisableCoalescing` opens one per host (`mimicry-nocoalescing` when run; decision 0037).
- **Page loads over HTTP/3, cold:** a new mimicry Transport knows nothing of HTTP/3: its first requests go over HTTP/2, the server's Alt-Svc starts a QUIC connection beside it, and later requests move to HTTP/3 once it is up (Chrome waits up to 300 ms for a QUIC attempt before going on TCP). The others are configured to force HTTP/3 from the first request, which no browser does for a site it has not seen advertise it. The protocol mix column shows it.
- **Page loads over HTTP/3, returning (`mimicry (returning)`):** a returning browser: new Transports sharing one `Config.AltSvc` cache that an earlier visit (one page load on a Transport of its own, not measured) filled, as a restarted Chrome starts with the Alt-Svc it saved. Each origin's first request races a fresh QUIC connection against TCP (TCP 300 ms later if QUIC is not up yet), as Chrome's does for an alternative it knows; no session tickets carry over, so no 0-RTT.
- **Idle memory over HTTP/3:** mimicry's idle state is a QUIC connection plus the HTTP/2 connection it learnt Alt-Svc on, which Chrome keeps open too.

## Layer 6: client rotation, a new client per identity

100 routines of one kind in one process, each sending GET /bytes/1024 to nginx one request at a time through the proxy, with credentials of its own. Every 10 requests a routine builds a new client with the library's ordinary constructor and the next identity's credentials (so a new tunnel or UDP association and a new handshake) and lets the old one go: **dropped**, abandoned as it is (code that makes a client per proxy and never closes it), or **closed**, with the library's close first. Each point first measures a new client alone, then warms the routines' first clients onto the protocol (three responses in a row), runs 1s, and measures 20s, longer than the other points so growth shows, sampling the process and the proxy every second. The proxy adds 5ms on the proxy's outgoing packets. The best impersonating client in each row is **bold**; net/http is the reference, never bolded.

- **Constructor and close, per library.** net/http: a new `http.Transport` (HTTP/2 through its `Proxy`), closed with `Transport.CloseIdleConnections`. mimicry: `mimicry.NewClient` (a `Config.Proxy` function returning the URL), closed with `Transport.CloseIdleConnections` (it has no `Close`). tls-client: `tls_client.NewHttpClient` with `WithProxyUrl`, closed with `HttpClient.CloseIdleConnections` (it has no `Close`). httpcloak: `httpcloak.NewSession` with `WithSessionProxy`, closed with `Session.Close`. azuretls: `azuretls.NewSession` then `SetProxy` (and `EnableHTTP3` for HTTP/3), closed with `Session.Close`, which closes its HTTP/1.1, HTTP/2 and HTTP/3 transports. Each is the adapter's `Close`, the same call the other layers end a client with.
- **HTTP/3.** A new mimicry client knows nothing of HTTP/3, so the routines' clients share one `Config.AltSvc` cache, as a caller who wants HTTP/3 from each new client does: the warm-up's clients learn nginx's, and each new client races QUIC against TCP as Chrome does for an origin it knows (TCP after Chrome's race delay). tls-client races too (`WithProtocolRacing`); httpcloak and azuretls force HTTP/3. A new client that loses the race goes on TCP: up to 1% of the responses may come over another protocol in these rows, as up to 1% may fail, and the last table gives the share. net/http has no HTTP/3 proxy: n/a.
- **New client under load:** from the switch (the old client's close included, when closed) to the new client's first response, p50 / p99, and the constructor's share (p50). **Alone:** before the load, one client at a time, each closed after its first response, 20 measured after one that warms the process up: medians of the constructor's time, the first request's, and the bytes and allocations of both together (the process's counters, nothing else running).
- **What is left, and its growth.** Once the window closes the routines finish their requests, nothing is closed, and after two GCs the live heap and the goroutines beyond what the process had before the routines' clients were built are divided by the routines. Growth is the least-squares slope over the per-second samples (the live heap as the last GC marked it). RSS is the process's resident memory (`/proc/self/statm`). Open at the proxy are the point's tunnels and UDP associations still open there: a connection a dropped client keeps shows there, a closed client's goes. A routine still in its request a minute after the window is stuck (last table); the end is read before its context is cancelled. Each point runs in a worker process of its own, so what it leaves ends with it.
- **Checked as above:** every response's protocol, and with the proxy that every identity that got a response opened a tunnel or an association, that it relayed each routine at least the body bytes it received, and over HTTP/3 that each routine's datagrams went through it.
