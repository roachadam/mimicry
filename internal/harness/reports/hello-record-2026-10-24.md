# ClientHello record version and GREASE ECH sets, 2026-10-24

The retaken default captures keep each ClientHello's TLS records
(`<name>.clienthello` lines 1–3, starting 0x16); the older lines are bare
handshake messages (starting 0x01). Every page capture taken today
(`connections`, `cookies-edge`, `cors-edge`, `headers-order`, and the
retaken `resume`, `resume-tls12`) records each connection's hello shape
and record version. Three samples per browser; Safari 26 from a second Mac.
`hellogen` now reads all of them.

## Record version

| | Chrome 155 | Firefox 158 | Safari 27 | Safari 26 |
|---|---|---|---|---|
| `.clienthello` records (3 samples) | 0x0301 ×3 | 0x0301 ×3 | 0x0301 ×3 | 0x0301 ×3 |
| page connections (3 samples each) | 0x0301 ×139 | 0x0301 ×132 | 0x0301 ×120 | 0x0301 ×120 |

Every sample of every page capture agrees; no other value seen. Captures
without records (`cors`, `proxy-auth`, `kinds*`, replays, Safari 26
`cookies`) show none and are not counted.

Implemented as `tls.record_version` (required: `Validate` accepts 0x0301
only, the one uTLS sends: its `conn.go` writes TLS 1.0 records before a
version is negotiated; `handshake.Spec` refuses anything else). `diff`
compares it where both sides kept it. The capture server now puts it in
the captured hello (`Profile.TLS.RecordVersion`), and `capture.Combine`
skips bare samples for the check.

## GREASE ECH, full handshakes

Page connections with a recorded shape, full hellos (TLS 1.2 resumptions,
which keep the full shape, included):

| | Chrome | Firefox |
|---|---|---|
| Cipher suites | AES-128-GCM ×118 | AES-128-GCM ×56, ChaCha20Poly1305 ×55 |
| Payload lengths | 144 ×32, 176 ×34, 208 ×27, 240 ×25 | 240 ×111 |

Chrome's set was {176, 208} from the `.clienthello` samples alone; with
every connection it is BoringSSL's four lengths. Safari sends no ECH.

## GREASE ECH, TLS 1.3 resumed hellos

| | Chrome (21: `resume` 3/3 samples, `cookies-edge` 2/3) | Firefox (21: `resume`, 7 per sample) |
|---|---|---|
| Cipher suites | AES ×21 | AES ×8, ChaCha ×13 |
| Payload lengths | 144 ×5, 176 ×2, 208 ×7, 240 ×7 | **400 ×21** |
| Everything else in the shape | the full hello's | the full hello's |

Chrome's length does not depend on resumption (BoringSSL draws GREASE
lengths at random); Firefox's does (NSS sizes the GREASE payload like the
inner hello, which carries the PSK). Implemented as
`tls.resumption.ech_payload_lengths` (required with ECH and resumption),
generated by `hellogen` from hellos carrying `pre_shared_key`;
`fingerprint.Plan.ResumedHello` swaps it in (precompiled, no per-connection
allocation). `TestResumptionMatchesBrowser` now diffs against the browser's
resumed hello with ECH sets from every resumed connection; the fallback to
the profile's shape for captures without one is gone.

## Not measured

- Firefox's 400 bytes come from the capture server's tickets only. That it
  follows the ticket's size is [INFERENCE]: a server issuing longer or
  shorter tickets may give another length, which the profile cannot
  describe yet.
- Resumed hellos' record version is 0x0301 in every capture; mimicry's
  resumed hellos are written by the same uTLS path.
