# Requests in 0-RTT, held, and retried after 425 Too Early: Chrome 155, Firefox 158, Safari 27 and Safari 26, 2026-10-26

Two scenarios (`internal/server/h3early.go`), three samples per browser,
all in `internal/harness/testdata/captures/` (Chrome and Firefox `.local-roots`;
Safari 27 and 26 unforced, Safari 26 on the second Mac):

| Scenario | Server | Page |
|---|---|---|
| `h3-early` | quic-go with 0-RTT, `max_idle_timeout` 3 s | `/` learns `h3-a`'s Alt-Svc; a fetch ends its HTTP/2 connection (GOAWAY, Safari's way to HTTP/3); the next goes over QUIC and stores a ticket. Then, 5 s apart so each finds the last connection idled out and resumes: fetch POST, PUT, DELETE, an XHR POST, a GET and a POST made together (`pair-get.so`, `pair-post.so`), a GET, a HEAD and an OPTIONS fetch, and last a form POST navigation to `form.so`, whose page asks for `/done` |
| `h3-too-early` | as `h3-early`, and every request whose stream started in a 0-RTT packet is answered **425 Too Early** (RFC 8470), with the body it would have had | the same |

The server tells 0-RTT requests apart by the packet type that carried
each stream's first STREAM frame, from quic-go's per-packet qlog trace
(`earlyStreams`): quic-go's HTTP/3 server only exposes
`r.TLS.HandshakeComplete`, which races with the handshake. Every 0-RTT
request in every sample got its 425.

Steps start on a fixed schedule (`NoWait`, `?t=` on each URL). Times
below are from the client's Finished (its first Handshake packet with
CRYPTO data), on the server's receive clock.

## 2. What the browsers' rules are

- Every browser sends only GET, HEAD and OPTIONS in 0-RTT and holds every
  other method until the handshake is done, whatever API made it
  (fetch, XHR, a form). No browser ever sent a request with a body in
  0-RTT.
- Every browser retries a 425 on the connection that got it, once the
  handshake is complete; none dialled a new connection for it.
- Where a held request leaves differs: Chrome right after its Finished,
  in a datagram of its own; Firefox in the Finished's datagram (the 4
  exceptions are necko handing the request to neqo against neqo writing
  the Finished, and are pinned in h3gen's `sampleGaps`); Safari once
  the handshake is confirmed, as its `requests_after_confirmed` first
  request does on a fresh connection.

## 3. Exploration before the committed page

An earlier page (its captures not kept) made each request after the
server closed the last connection. Firefox does not resume after a
server's close the way the page needed: it sends the next request over
TCP and resumes QUIC beside it, so the request never meets a resumed
connection. The committed page waits for an idle timeout instead (the
server announces 3 s), which every browser treats as a silent close and
resumes after.

## 4. In mimicry

- New profile field `http3.early_data` (`methods`, `held_with_finished`,
  `retry_too_early`), required with `quic.zero_rtt` and only then,
  derived by `h3gen` (`cmd/h3gen/edge_early.go`) from both pages, which
  are now in `server.H3EdgeCaptures`: Chrome `GET HEAD OPTIONS`, retry;
  Firefox the same plus `held_with_finished`. Safari's profiles have no
  QUIC resumption, so no `early_data` either.
- `internal/h3`: a request whose method is not in `methods` waits for the
  handshake (`awaitHandshake`) and, for Firefox, rides with the Finished
  (`internal/quic`: `HoldFinished`/`ReleaseFinished`, `HandshakeComplete`).
  A 0-RTT request answered 425 goes again on the same connection where
  the profile retries and its body can be read again (`GetBody`).
- `TestHTTP3EdgeMatchesBrowser` replays both pages for every profile.
  Besides each request's connections and delay it now compares, on a
  connection that sent 0-RTT, each of its streams: in 0-RTT, held with
  the Finished or after it, or sent again after a 425 in which packet
  type (`earlyStream`). Chrome and Firefox match every sample.
- `TestQUICInterop` row `0rtt-too-early`: quic-go answers 425 to the
  request it got before its handshake completed; the client gets a 200
  from the same, resumed connection, the server having sent exactly one
  425.

## 5. Gaps pinned

- Firefox's declined TCP connections beside its retries
  (`h3EdgeGaps`: `firefox-158-macos/h3-too-early … declined`): which
  retries get one varies between samples.
- Safari's resumed connections (`h3EdgeGaps`, both pages, both
  versions): Safari resumes after an idle timeout as after its own close,
  with Chrome's method rule; mimicry's Safari connections are fresh, so
  every request's connection, stream and resumption differ.
- Safari's resumed connections start 5–11 ms after the request that
  needs them (5–9 ms after the pair), after both of a GET and a POST
  made together, so its `pair-post.so` is the connection's trigger;
  mimicry's start at once, before or after its POST is made as the test
  process schedules them (`h3EdgeSchedulingGaps`: skipped, not required
  to appear).
- Safari's OPTIONS fetch: its kinds captures have none, so mimicry
  refuses it (`ErrNotMeasured`) and the replay skips it, pinned; the
  connections after it are numbered one lower.
- Firefox's 4 held requests that left after the Finished (h3gen
  `sampleGaps`).
