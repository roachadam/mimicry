# Other clients against real browsers, 2026-10-23

How close tls-client, httpcloak and curl-impersonate come to the browsers
captured in `testdata/captures/` (Chrome 155, Firefox 158, Safari 27 on
macOS), judged by the same capture server and diff. mimicry is included as a
baseline, but it is **not independent evidence**: its profiles were built from
these captures, so matching them is expected.

## Method

Each client used its closest preset, ran three times against a fresh
`set-cookie` scenario server (`cmd/clientcapture`), loading `/` (receiving
the real-world-shaped cookie jar) and then `/again` on the same connection
with its own cookie handling. Captures are in `testdata/clients/`.

| Client | Version | Chrome 155 | Firefox 158 | Safari 27 |
|---|---|---|---|---|
| curl-impersonate | 2.3.0 (2026-10-20) | `curl_chrome152_macos` | `curl_firefox155` | `curl_safari270` |
| tls-client | `ca3c9e4` (2026-10-22) | `chrome_152` | `firefox_148` | `safari_16_0`, `safari_ios_26_0` |
| httpcloak | `3a426f9` (2026-10-14) | `chrome-155-macos` | `firefox-148-macos` | `safari-latest` |
| mimicry | `42dd6f3` | `chrome-155-macos` | `firefox-158-macos` | `safari-27-macos` |

tls-client sends only headers its caller sets, so its probe sent the captured
browser's navigation headers in the browser's order (as its README
advises): its header rows below reflect that input, not tls-client. curl and
httpcloak sent their own.

Compared: the first request (`cmd/diff`: ClientHello, HTTP/2 SETTINGS,
WINDOW_UPDATE, HEADERS priority, pseudo-header order, headers and values);
each navigation field's HPACK representation and Huffman use against the
browser's first block; and the cookies on `/again` against the browser's
first cookie-carrying request in the same scenario (one field per cookie or
one joined field, order, representation).

Not compared: anything after the second request (flow control, priorities
of later streams, connection reuse, replayed real pages), HTTP/3.

## Results

Differences per client; *version* marks ones a newer preset would be expected
to fix (user agent, `sec-ch-ua`, values that changed between versions).

### Chrome 155

| | TLS | HTTP/2 | Headers | HPACK (navigation) | Cookies |
|---|---|---|---|---|---|
| curl `chrome152_macos` | trust anchors (0xca34) list reshuffled per connection; signature_algorithms without GREASE | match | `accept` without `image/jxl` (*version*), extra `cache-control: max-age=0` | match | **one joined field** |

| mimicry | match | match | match | match | match |

Chrome 155's trust anchor list was identical across three separate browser
launches; httpcloak notes that this varies with the Chrome version, so the
152 presets may be right for 152.

## What stands out

- **Cookies are where every other client differs.** Every browser sends each
  cookie as its own HPACK field. curl-impersonate (all targets) and
  httpcloak's Safari preset send one joined field; tls-client sends them in
  reverse creation order; none of tls-client or httpcloak's Firefox/Safari
  presets never-index the short ones. Only httpcloak's Chrome preset matches.
- **Firefox's connection opening.** No other client opens Firefox's way:
  first request on stream 3, a 12451840 stream WINDOW_UPDATE right after it.
- **Chrome's extension shuffle.** tls-client's `chrome_152` sends one fixed
  order, which no Chrome since 110 does.
- **Navigation as a navigation.** curl's Firefox and Safari wrappers send
  fetch-style or same-origin metadata on the first page load.

## Reproduce

In `harness/`, with the clients built as in `cmd/clientcapture`'s doc:

```sh
go run ./cmd/clientcapture -scenario set-cookie -out DIR -name NAME -- CLIENT {url}...
go run ./cmd/diff testdata/captures/chrome-155-macos.json DIR/NAME.json
```

The probes used for the Go libraries (a tls-client and an httpcloak program
loading `/` and `/again` with a cookie jar) were throwaway; curl ran as
`curl_<target> -sk -o /dev/null -b '' {url}/ {url}/again`.
