# Request kinds and cookies in Chrome 155, Firefox 158 and Safari 27, 2026-10-23

What the `kinds` and `kinds-http1` scenarios (`internal/server/kinds.go`) show
about how each browser sends each kind of request and handles cookies: the
evidence for request kinds and the cookie jar (HANDOFF step 9). Captures:
`testdata/captures/*.kinds.pagetrace.json.gz` and
`*.kinds-http1.pagetrace.json.gz`, three samples per browser (separate
launches for Chrome and Firefox). Every finding below was the same in all
three samples and, where it applies, on every target host.

## Method

One page on `www.kinds-a.test` makes each request kind against itself
(same-origin), `static.kinds-a.test` (same-site) and
`cdn.kinds-b.test` (cross-site): scripts (plain, CORS, CORS with
credentials), stylesheets, images (plain, CORS, high priority), fonts,
iframes, `fetch()` (default, credentials include and omit, no-cors, JSON
POST, a custom header, high and low priority), XHR and `sendBeacon`, one
after another; plus, in its HTML, a head stylesheet, preloads, blocking,
deferred and async scripts and an `<img>`; redirects across sites; and a
form-submit POST navigation at the end. The page's document sets cookies of
every SameSite value and non-standard ones; the cross-site host sets its
own when first loaded as a third party. `kinds-http1` is the same page with
every host offering only HTTP/1.1.

## Priorities by kind (HTTP/2; `priority` header / HEADERS weight)

| Request | Chrome | Firefox | Safari (no weights) |
|---|---|---|---|
| Navigation, iframe | `u=0, i` / 255 | navigation `u=0, i` / 41; iframe `u=4` / 21 | `u=0, i` |
| Stylesheet (head or script-made) | `u=0` / 255 | `u=2` / 21 | `u=1, i` |
| Script, blocking in the head | `u=1` / 219 | `u=2` / 21 | `u=1, i` |
| Script, defer / async / script-made | none / 146 | none / 21 | defer and script-made `u=1, i`; async `u=3, i` |
| Preload script | `u=1` / 219 | `u=1` / 41 | `u=1, i` |
| Font (preload or FontFace) | `u=1` / 219 preload, `u=0` / 255 FontFace | `u=2` / 31 preload, none / 31 FontFace | `u=3, i` |
| Image in the HTML | `u=2, i` / 182 | `u=5, i` / 11 | `u=5, i` |
| Image made by script | `i` / 146 | `u=5, i` / 11 | `u=5, i` |
| Image, `fetchpriority=high` | `u=1, i` / 219 | `i` / 31 | `u=3, i` |
| `fetch()`, XHR | `u=1, i` / 219 | fetch `u=4` / 21; XHR none / 21 | `u=3, i` |
| `fetch()` high / low | `u=1, i` / 219; `i` / 146 | none / 31; `u=5` / 11 | `u=1, i`; `u=5, i` |
| `sendBeacon` | `u=4, i` / 109 | `u=6` / 1 | `u=7, i` |

So a kind alone does not fix the priority: how the request is made (a
blocking script versus an async one, an image in the HTML versus one made by
script) and `fetchpriority` change it, in every browser.

## Other per-kind differences

- `sec-fetch-mode` for fonts: `cors` in Chrome and Firefox, `no-cors` in
  Safari (FontFace).
- `accept` per kind: images, stylesheets, documents each have their own;
  Firefox's font accept is `application/font-woff2;q=1.0,…`, the others
  `*/*`.
- **`Sec-Fetch-Storage-Access`** on cross-site requests with credentials:
  Chrome `active`, Firefox `none`, Safari never; same over HTTP/2 and
  HTTP/1.1, absent without credentials.
- **Safari's redirected `fetch()`**: the request after a redirect drops every
  `sec-fetch-*`, `accept-language` and `priority`, and adds `origin`;
  redirected images keep theirs. Chrome and Firefox send `sec-fetch-site:
  cross-site` after any cross-site hop, as the Fetch spec says.
- HTTP/1.1 header casing and order differ per kind as over HTTP/2 (e.g.
  Chrome moves `sec-ch-ua-platform` first for subresources); the captures
  hold every kind's lines.

## Connections

| | Chrome | Firefox | Safari |
|---|---|---|---|
| Separate connection for requests sent without credentials (`credentials: omit`; cross-origin requests that carry none: `crossorigin=anonymous`, a default or no-cors `fetch()` to another origin, fonts) | yes, to every host, same-origin included | **unsettled**: to the same-site host in all three samples of the final run; not to the cross-site host; not at all in an earlier run of the page without its HTML elements | no |
| Cross-site iframe | its own connection (partitioned by the frame's site) | shares the host's connection | shares |
| Handshakes never used for a request | one more per host (preconnects) | none | none |
| Resumed TLS sessions (pre_shared_key) | HTTP/1.1: 2–3 of 12–13 connections; HTTP/2: none | HTTP/1.1: 1–2 of 11–12; HTTP/2: none | none |

## Cookies

| | Chrome | Firefox | Safari |
|---|---|---|---|
| Sent cross-site (third-party) | `SameSite=None`, partitioned | `None`, partitioned **and no SameSite** | **partitioned only** |
| SameSite unset treated as | Lax | None | (third-party blocked anyway) |
| Order in the Cookie header | creation | creation | by name |
| Kept and sent back byte for byte | quoted (`"Ab+/cd=="`), spaces, comma, backslash, UTF-8, JSON, empty value | same | same, except UTF-8 |
| UTF-8 value `café` | sent as set | sent as set | **sent as `cafÃ©`** (bytes read as Latin-1, re-encoded) |
| Cookie without `=` (`knoeq`) | sent as `knoeq` | sent as `knoeq=` | dropped |
| Rejected | over 4096 bytes, Domain not matching, `__Host-` with Domain, expired, `Max-Age=0` | same | same |

All three accept everything Go's `net/http` drops or re-quotes (backslash,
UTF-8, JSON; spaces and commas sent unquoted), so a browser-faithful jar
must keep raw values.

## Corrections

A first run served the page under `*.localhost`. WebKit treats every
`*.localhost` host as a site of its own, so Safari reported its same-site
requests as `cross-site` and withheld the site-wide cookie from them; the
page now uses `*.test` names (resolved for Safari by the capture tool's DNS
stub), and Safari reports `same-site` like the others. The replays moved to
`*.test` too, and Safari's were recaptured with its content blocker turned
off: its nytimes replay still reaches 1217 of 1286 requests, so that gap is
Safari's own behaviour, cause not yet established.

Deriving the profiles' kinds from these captures (`cmd/kindsgen`) showed
what the first reading missed: fonts loaded by CSS `@font-face` differ
from `FontFace` loads in Firefox, which sends `accept-encoding: identity`
for them; Chrome and Firefox send the stylesheet's URL as their Referer,
Safari the page's. Header order also differs within a kind, by method,
site relation, CORS check and redirect (Safari most), which the profiles
now record as variants.
