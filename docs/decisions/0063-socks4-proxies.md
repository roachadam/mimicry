# 0063: SOCKS4 and SOCKS4A proxies, as Chrome, Firefox and Safari send them

- Status: Accepted
- Date: 2026-11-08 (updated 2026-11-10: rebased onto 0065, 0066 and 0068; Brave, Chrome 157 and Safari 27 captured)
- Commits: `785679d`

**Summary.** `Config.Proxy` takes `socks4://` and `socks4a://` URLs. Through
`socks4://` mimicry looks the host up itself (`Config.Resolver`, IPv4) and
sends its address, as Chrome, Edge, Brave and Firefox do; through
`socks4a://` it sends the host name (SOCKS4A), as Firefox does with remote
DNS and Safari always does. Chromium has no SOCKS4A, so Chrome, Edge and
Brave profiles refuse `socks4a://`; Safari never resolves for a SOCKS4
proxy, so the Safari profiles refuse `socks4://`. A generated
`proxy.socks4` profile section (hellogen) holds what the captures show;
Safari 26's is assumed from Safari 27's captures, not captured (the
maintainer's decision). Every profile without one (the iPhone profiles, for
good: iOS offers no SOCKS4 route; Chrome 155, Firefox 158) returns `ErrNotMeasured`. Amends [0014](0014-proxies.md).

## Problem

tls-client takes `socks4://` and `socks4a://` proxies; mimicry took
`http`, `socks5` and `socks5h` only
([#106](https://github.com/roachadam/mimicry/issues/106)). Chrome
(`--proxy-server=socks4://`), Firefox (`network.proxy.socks_version` 4)
and, through a hidden system setting, Safari can use SOCKS4 proxies, so a
caller with one had no way to send through it as a browser would.

## Options

- **Send what SOCKS4 allows, unmeasured.** The protocol leaves the user ID,
  4 or 4a, the SOCKS4A placeholder address and who resolves the host to
  the client: guessing any of them is a fingerprint the proxy can see.
- **Capture first, then model per browser** (chosen), as decision 0014
  did for SOCKS5.
- **Refuse Safari** because its SOCKS4 needs a setting no UI offers
  (below). Rejected: when so configured it is what Safari sends, and the
  proxy sees Safari's bytes; the profile says how it was configured.

## Decision

- Schemes `socks4` (local lookup, IPv4 address in DSTIP) and `socks4a`
  (the host name after USERID, DSTIP the profile's placeholder). An IPv4
  literal goes out as itself through either; an IPv6 literal, or a host
  with no IPv4 address through `socks4://`, is an error. With several IPv4
  addresses the first the resolver returns is sent.
- `proxy.socks4`, generated by hellogen from the `proxy-socks4` and
  `proxy-socks4a` captures (as 0065's `proxy.https`): `{}` for Chrome,
  Edge and Brave; `{"hostname": true, "hostnameDstip": "0.0.0.1"}` for
  Firefox; `{"hostname": true, "hostnameOnly": true, "hostnameDstip":
  "0.0.0.16"}` for Safari 27. `hostnameOnly` (a browser that, given a
  SOCKS4 proxy, sent SOCKS4A anyway) makes `socks4://` an
  `ErrNotMeasured` naming `socks4a://`. Nil means not measured.
- USERID is empty, as browsers send it; a URL's user name goes there,
  a deviation only the proxy sees (a SOCKS4 user ID is how some proxies
  identify clients). A URL with a password is an error: SOCKS4 has none.
- No HTTP/3 through SOCKS4 (it has no UDP), whatever `HTTP3OverSOCKS5`
  or `ConnectUDPProxy` say ([0038](0038-http3-over-socks5.md) covers
  SOCKS5, [0066](0066-http3-over-connect-udp.md) http and https proxies
  only), and no WebSockets through it (never captured): `ErrNotMeasured`.
- As through every proxy, no DNS HTTPS record is looked up, so real ECH
  is never sent through SOCKS4 ([0068](0068-real-ech.md)); the
  `socks4://` lookup is the A record alone. TLS sessions are kept per
  proxy URL ([0062](0062-saved-tls-tickets.md)) and forgotten with it
  ([0040](0040-idle-connection-cleanup.md)); through SOCKS4 they resume
  as directly, as through SOCKS5 (`connectNoResume` covers CONNECT
  tunnels only).
- An IPv6 target, a NUL in a field, or a failed lookup through
  `socks4://` fails before the proxy is dialled and is not a
  `*ProxyError`: no proxy was asked, and a caller rotating proxies on
  `*ProxyError` (decision 0033) would gain nothing by trying another.
  This narrows 0033's "every failure before the server is reached" to
  failures on the way to or at a proxy.
- The `socks4://` lookup follows 0068's rule for HTTPS records: with
  `Config.DialContext` set and no `Config.Resolver` with its own `Dial`,
  a lookup would leave outside the caller's dialer (and could reveal the
  host on another path), so a host name through `socks4://` is refused
  the same way (not a `*ProxyError`), naming `socks4a://` and such a
  resolver. IP literals still go.

## Evidence

- Harness scenarios `proxy-socks4` and `proxy-socks4a` (the capture
  proxy records the raw request), 3 samples each:
  - Chrome 156.0.8078.80 (macOS), 156.0.8078.81 (Windows), Chrome
    157.0.8103.38 (Linux, WSL), Edge 157.0.4341.42 (macOS, Windows),
    2026-11-08; Chrome 157.0.8103.39 (macOS) and Brave 1.99.55 (Chromium
    157; macOS, Windows, Linux), 2026-11-10; `proxy-socks4`: `04 01
    <port> 7f000001 00` in every sample (Chrome on macOS: two tunnels per
    sample).
  - Firefox 159 (159.0 on macOS, 159.0.1 on Windows and Linux),
    `proxy-socks4` (`socks_remote_dns` off): the same on all three;
    `proxy-socks4a` (`socks_remote_dns` on): `04 01 <port> 00000001 00`
    then `capture.mimicry.test` and NUL.
  - Safari 27.0.1 on macOS 27.0.1, 2026-11-10, both scenarios (the same
    setting serves both): `04 01 <port> 00000010 00` then
    `capture.mimicry.test` and NUL, every sample.
- Chrome with `--proxy-server=socks4a://`: nothing reached the proxy (an
  ad-hoc run before the scenarios; the capture tool refuses the scenario
  for Chromium browsers, Edge and Brave included).
- Safari, 2026-11-10, a throwaway SOCKS logger on this Mac (Safari 27.0.1,
  macOS 27.0.1) and the second Mac (Safari 26.2, macOS 26.2), loading
  `http://192.0.2.x/`:
  - a proxy script answering `SOCKS host:port`: Safari's SOCKS5 greeting
    (`05 01 00`); answered `05 FF`, `00 5B` or a close, Safari never
    tried SOCKS4 (on the second Mac, and with `00 5B` here, it then
    connected directly); `SOCKS4 host:port`: ignored, Safari connected
    directly. Both Macs.
  - the SOCKS proxy setting (`networksetup -setsocksfirewallproxy`):
    SOCKS5, as above (this Mac).
  - the SOCKS proxy setting with `kCFStreamPropertySOCKSVersion` set to
    `kCFStreamSocketSOCKSVersion4` in the service's proxies (a key
    CFNetwork reads from a proxy dictionary; no UI, `networksetup` option
    or configuration profile writes it: `scutil --prefs` does): `04 01
    0050 c000020e 00` for an IP address, and SOCKS4A with DSTIP
    `0.0.0.16` and the name for `http://example.com/`, from
    `com.apple.WebKit.Networking` (`lsof`). With a proxy script the key
    changes nothing (still SOCKS5). A command-line `URLSession` given the
    key in `connectionProxyDictionary` also spoke SOCKS4.
- `TestProxyMatchesBrowser` (`socks4`, `socks4a`) compares mimicry's
  request through the capture proxy with each sample (Safari's
  `proxy-socks4` through `socks4a://`), and its tunnelled hello with the
  profile's; setting Safari's `hostnameDstip` to `0.0.0.1` fails it.
  `TestUnmeasuredProxyIsAnError` covers a profile without `proxy.socks4`,
  `socks4://` for a hostname-only browser, Chrome's `socks4a://` and a
  WebSocket through SOCKS4; `TestSOCKS4` (`internal/proxy`) checks the
  request bytes against the captured ones and each refusal;
  `TestProxyErrors` checks a refused and an unanswered SOCKS4 proxy are
  `*ProxyError`s.

## Consequences

- Chrome 155 and Firefox 158 were not captured, by the maintainer's
  decision (2026-11-10): those versions age out, and installing them again
  for one scenario is not worth it. They refuse SOCKS4
  (`ErrNotMeasured`; EVIDENCE.md, Not covered).
- Safari 26 (safari-26-macos) is not captured: the second Mac, where it
  runs, takes the SOCKS version key only from someone at its screen (over
  ssh, `scutil --prefs` is denied). By the maintainer's decision
  (2026-11-10) its SOCKS4 is assumed to be Safari 27's: its
  `capturesFrom` names safari-27-macos for `proxy-socks4` and
  `proxy-socks4a`, so hellogen derives the same `proxy.socks4` and the e2e
  tests check it against Safari 27's captures. This is the one exception
  to inheriting from older versions only
  ([0035](0035-version-policy-and-capture-inheritance.md)):
  `assumedFromNewer` in `cmd/profilegen` lists it, and the policy check
  (`TestCheckPolicyRefuses`) refuses any other profile or scenario naming
  a newer version. What supports the assumption: Safari 26.2 behaved as
  27.0.1 in every proxy-script SOCKS test above, and both send the same
  SOCKS5 handshake; its SOCKS4 bytes themselves were never seen. A real
  capture replaces the inheritance (the commands are in
  docs/capturing.md).
- The iPhone profiles (safari-26-ios, safari-27-ios, chrome-157-ios,
  firefox-159-ios) refuse SOCKS4 for good, the maintainer's decision
  (2026-11-10); no phone test is planned. iOS offers no SOCKS4 route: the
  Wi-Fi proxy's Manual setting and configuration profiles take an HTTP
  proxy only, a proxy script's `SOCKS` is SOCKS5 on the networking stack
  iOS shares with macOS (as measured on macOS above), and the hidden SOCKS
  version key has no way to be set on iOS ([INFERENCE] for iOS itself,
  not tried on a phone). The proxy sees the handshake, so sending a form
  no iPhone sends would be a fingerprint the proxy could see. The capture
  tool refuses the SOCKS4 scenarios on the iPhone with this reason
  (`Scenario.UnsupportedOnIOS`), and macOS Safari's captures are never
  inherited on iOS (`Scenario.NotInheritedOnIOS`).
- Safari's SOCKS4 is what Safari sends when the Mac is set up that way, a
  configuration few users have; a proxy that sees a Safari SOCKS4A
  request with DSTIP `0.0.0.16` sees what that Mac would send.
- Through `socks4://` the lookup happens on the client, as in the browser:
  the DNS query leaves from the client's network, not the proxy's.
- Capturing Safari's SOCKS4 sends every URL the Mac loads to the capture
  proxy, which passes other hosts through unrecorded: the capture tool
  runs those scenarios alone (docs/capturing.md).

## Revisit when

A browser is seen picking another address than the first, retrying the
next address after a refusal, or sending a user ID; Safari 26 can be
captured at the second Mac (then drop the exception); or an iOS setting
is found that makes the phone speak SOCKS4 (which would reopen the
iPhone's refusal).
