# Proxies: what Chrome 155, Firefox 158 and Safari 27/26 send a proxy, 2026-10-24

Scenarios `proxy-connect`, `proxy-socks5`, `proxy-plain`, `proxy-auth` (the
resume page: a new connection per request, three hosts) and
`proxy-plain-auth`, three samples each, the capture proxy in front of the
capture server. Chrome and Firefox on this Mac; Safari 27 here and Safari 26
on the second Mac through a PAC script. Credentials were answered over
Chrome's DevTools protocol and Firefox's WebDriver BiDi.

## Through a tunnel nothing changes

Every browser's first request through a CONNECT or SOCKS5 tunnel, ClientHello,
HTTP/2 preface and headers, equals its direct one (the capture tool's
comparison for Chrome and Firefox; SETTINGS, window update and first request
compared by hand for both Safaris).

## CONNECT

| | Request headers, in order |
|---|---|
| Chrome | `Host: <target>`, `Proxy-Connection: keep-alive`, `User-Agent: <its UA>` |
| Firefox | `User-Agent: <its UA>`, `Proxy-Connection: keep-alive`, `Connection: keep-alive`, `Host: <target>` |
| Safari 27, 26 | `Host: <target>`, `Proxy-Connection: keep-alive`, `Connection: keep-alive` (no User-Agent) |

The target always carries its port (`host:443` form).

## SOCKS5

All four: greeting `05 01 00` (only "no authentication"), then CONNECT with the
host name (`ATYP 03`), never a resolved address: the proxy resolves.

## Plain HTTP through an HTTP proxy

Absolute-form request lines (`GET http://host:port/path HTTP/1.1`). Chrome
sends `Proxy-Connection: keep-alive` where it puts `Connection`; Firefox and
Safari keep `Connection: keep-alive`. Safari first tries a CONNECT to the same
host and port (an automatic HTTPS upgrade), then falls back when the proxy
refuses it.

The rest of these requests' headers are a non-secure origin's: no
`Sec-Fetch-*`, no `sec-ch-ua*`, `Accept-Encoding: gzip, deflate`; see
[`plain-http-2026-10-24.md`](plain-http-2026-10-24.md), which mimicry now
follows with or without a proxy.

## Credentials

| | Chrome 155 | Firefox 158 | Safari 27 |
|---|---|---|---|
| First CONNECT to a proxy | without credentials; 407; again on the same connection with them | the same | the same |
| Later CONNECTs | credentials unasked | credentials unasked | **every one** without credentials first, 407, then again with them |
| CONNECT with credentials | its CONNECT headers, `Proxy-Authorization` last | the same | **reordered**: `Host`, `Connection`, `Proxy-Authorization`, `Proxy-Connection` |
| Forwarded plain requests | first without, 407, again on the same connection; then unasked | the same | **unasked from the first** (and still CONNECT-challenged for its HTTPS-upgrade attempts) |
| `Proxy-Authorization` in a forwarded request | after `Proxy-Connection`, or after `Content-Length` when there is a body | before `Connection` unasked; **last** on the request answering the challenge | right after `Accept-Encoding` |

Chrome's net log (`--log-net-log`) attributes its extra 407-only connections
before the first success to speculative preconnects (`is_preconnect: true`),
which mimicry does not make; the navigation's own connection follows the flow
above. Safari's forwarded-request row was confirmed on a freshly started
Safari, so it is not a credential remembered from earlier runs.

### Giving Safari credentials

Safari never answers a proxy challenge itself: WebKit leaves proxy
authentication to CFNetwork (`NetworkSessionCocoa.mm`: "Proxy authentication
is handled by CFNetwork internally"). These setups gave CFNetwork no
credentials it would use, with Safari and with a plain `URLSession` probe
alike (one CONNECT, 407, "Authentication error"):

- the PAC script with Basic credentials as Internet passwords (`htsx`,
  `htpx`) in the System keychain;
- manual web and secure web proxies with a password (`networksetup … on
  mimicry capture`; it saved only an `htpx` login-keychain entry), with and
  without a matching `htsx` entry, Safari restarted;
- a `com.apple.proxy.http.global` configuration profile (manual proxy,
  `ProxyUsername`, `ProxyPassword`; it must be a device profile,
  `PayloadScope: System`).

What worked: with the configuration profile installed, macOS itself raised a
proxy login dialog with fields; once the credentials were typed there,
CFNetwork answered every proxy challenge, for Safari and every other app.
Safari 26 was not measured; its profile copies Safari 27's credential rules
(every other proxy claim matched Safari 27's on its own captures).
