# Proxies: what Chrome 155, Firefox 158 and Safari 27/26 send a proxy, 2026-10-24

Scenarios `proxy-connect`, `proxy-socks5`, `proxy-plain`, `proxy-auth` (the
resume page: a new connection per request, three hosts) and
`proxy-plain-auth`, three samples each, the capture proxy in front of the
capture server. Chrome and Firefox on this Mac; Safari 27 here and Safari 26
on the second Mac through a PAC script. Credentials were answered over
Chrome's DevTools protocol and Firefox's WebDriver BiDi.

## Through a tunnel nothing changes

Every browser's first request through a CONNECT or SOCKS5 tunnel, ClientHello,
HTTP/2 preface and headers, equals its direct one (the capture tool's
comparison for Chrome and Firefox; SETTINGS, window update and first request
compared by hand for both Safaris).

## CONNECT

| | Request headers, in order |
|---|---|
| Chrome | `Host: <target>`, `Proxy-Connection: keep-alive`, `User-Agent: <its UA>` |
| Firefox | `User-Agent: <its UA>`, `Proxy-Connection: keep-alive`, `Connection: keep-alive`, `Host: <target>` |
| Safari 27, 26 | `Host: <target>`, `Proxy-Connection: keep-alive`, `Connection: keep-alive` (no User-Agent) |

The target always carries its port (`host:443` form).

## SOCKS5

All four: greeting `05 01 00` (only "no authentication"), then CONNECT with the
host name (`ATYP 03`), never a resolved address: the proxy resolves.

## Plain HTTP through an HTTP proxy

Absolute-form request lines (`GET http://host:port/path HTTP/1.1`). Chrome
sends `Proxy-Connection: keep-alive` where it puts `Connection`; Firefox and
Safari keep `Connection: keep-alive`. Safari first tries a CONNECT to the same
host and port (an automatic HTTPS upgrade), then falls back when the proxy
refuses it.

The rest of these requests' headers are a non-secure origin's: no
`Sec-Fetch-*`, no `sec-ch-ua*`, `Accept-Encoding: gzip, deflate`. mimicry does
not model non-secure origins yet (with or without a proxy); that is the next
item.

## Credentials

Chrome and Firefox alike:

1. The first request to a proxy goes without credentials; the proxy answers
   407 (Basic).
2. The request is sent again on the same connection with
   `Proxy-Authorization`.
3. Every later request to that proxy carries the credentials unasked: new
   tunnels to every host, and forwarded plain requests.

`Proxy-Authorization` goes last in a CONNECT (both), last in a forwarded
request for Firefox, and right after `Proxy-Connection` for Chrome.

Chrome's net log (`--log-net-log`) attributes its extra 407-only connections
before the first success to speculative preconnects (`is_preconnect: true`),
which mimicry does not make; the navigation's own connection follows the flow
above.

Safari has no login dialog for proxies: macOS shows "Enter the password for
the HTTP proxy in System Settings", and System Settings has no password field
for a PAC-configured proxy. Safari's credential flow is not measured.
