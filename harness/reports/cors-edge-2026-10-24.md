# fetch() redirects: what Chrome 155, Firefox 158 and Safari 27/26 do, 2026-10-24

Source: the new `cors-edge` scenario. From `https://www.kinds-a.test`, the
page makes its fetches in order (`server.CORSEdgeSteps`), over HTTP/2, to
the same host (`.so`) or to `https://cdn.kinds-b.test` (`.cs`). Each is
answered with a redirect to `<label>.hop1`, and so on up to `.hop<Hops>`,
which is answered 200.

Three samples per browser, Safari 26 on the second Mac. Every browser's
three samples were identical, the server's port aside: the same requests,
on the same connections (one per host), in the same order, with the same
header names in the same order.

## Step by step

"→" is the next request on the wire. Empty cells match the cell to their
left.

| Step | Chrome | Firefox | Safari 27, 26 |
|---|---|---|---|
| `acao-redirect.cs`: cross-site GET, 302 with `Access-Control-Allow-Origin` | GET, → GET `.hop1` (with `Origin`) | | |
| `noacao-redirect.cs`: the same 302 without it | GET only: **`.hop1` never requested** | | |
| `noacao-redirect-pf.cs`: the same, with `X-Mimicry` (preflighted) | OPTIONS, GET only: **no `.hop1`** | | |
| `m-put-301.so`, `m-put-302.so`: same-origin PUT, body `x` | PUT, → **PUT** `.hop1`, body 1 byte, `content-type: text/plain;charset=UTF-8`, `Origin` | | |
| `m-delete-301.so`, `m-delete-302.so` | DELETE, → **DELETE** with the body, as PUT | | |
| `m-put-303.so`, `m-delete-303.so` | → **GET**, no body, no `content-type`, **no `Origin`** | | → GET, no body, no `content-type`, **with `Origin`** |
| `m-post-301.so`, `-302`, `-303` | → GET, no body, no `content-type`, no `Origin` | | → GET, no body, no `content-type`, with `Origin` |
| `chain.so`: same-origin GET, 25 redirects | `chain.so`, `.hop1` … **`.hop20`**: 21 requests; `.hop21` never | | |

So:
- a CORS request's redirect gets the CORS check, as the Fetch standard
  says: without `Access-Control-Allow-Origin` no browser follows it, with
  or without a preflight before;
- the method rules are the Fetch standard's in every browser: only POST
  changes on 301 and 302; 303 makes a GET of anything; PUT and DELETE keep
  their method, body and `Content-Type` on 301 and 302. Go's
  `http.Client` makes a GET of PUT and DELETE too;
- every browser stops after 20 redirects (Fetch standard: 20); Go's
  `http.Client` stops after 10;
- the one difference: the GET a redirect makes of a POST, PUT or DELETE
  keeps the request's `Origin` in Safari (WebKit keeps the request's
  headers and strips only the body ones), not in Chrome and Firefox (a
  same-origin GET sends none).

## What mimicry does now

- `refusedRedirect` (`redirect.go`): a `fetch()` or XHR in CORS mode to
  another origin (the requests that send `Origin` for being cross-origin;
  `sending.corsOrigin`) whose 301/302/303/307/308 with a `Location` fails
  the CORS check (`checkCORS`, shared with the preflight's answer) returns a
  `*CORSError` with `Redirect` set, the redirect's status and headers, and
  its body closed. `http.Client` never sees the redirect, so nothing more
  is sent. `Request.IgnoreCORS` follows it.
- `browserHop` (`redirect.go`): each hop `http.Client` builds comes back to
  `RoundTrip` with `req.Response` set. The method is recomputed from the
  request the redirect answered, as sent (`req.Response.Request`), by the
  rules above. Where `http.Client` turned a PUT or DELETE into a GET, or
  dropped a body for good on an earlier hop, the hop is cloned with the
  method, a fresh body from `GetBody`, its length and the body headers
  (`Content-Type`, `-Encoding`, `-Language`, `-Location`) restored. A body
  without `GetBody` is an error, not the GET `http.Client` built. A chain
  of more than 20 redirects is an error before anything is sent.
- `NewClient` sets `CheckRedirect` to follow everything (`followRedirects`):
  the Transport's limit is the only one.
- `redirects.method_change_origin` (new profile section, hand-edited):
  `keep` for Safari 27 and 26, `drop` for Chrome and Firefox. `resolve`
  sends `Origin` on a CORS-mode fetch()/XHR GET that a redirect made of
  another method (`redirectedToGet`) when the rule says `keep`; a profile
  without the section gets `ErrNotMeasured` there.

## Why the Transport fixes the hop, not a redirect-following wrapper

The task allowed mimicry to follow redirects itself for `NewClient`'s
client. Three designs were weighed:

1. **The Transport corrects the hop `http.Client` built** (chosen). No API
   change; it works for `NewClient` and for any `http.Client` around a
   `Transport`, so every client sends the browser's requests.
   `http.Client` keeps owning redirects: `CheckRedirect`,
   `ErrUseLastResponse`, a client `Jar` (with `NewTransport`), `Timeout`,
   and its sensitive-header stripping all apply as documented. The cost: a
   caller's `CheckRedirect` sees the hops as `http.Client` built them (a
   PUT answered 301 appears as a GET in `req`/`via`), while what is sent,
   and `resp.Request`, are the browser's.
2. **A wrapper RoundTripper for `NewClient` that follows redirects itself.**
   It would have to replace `http.Client`'s redirect loop (Location parsing,
   header copying and stripping, `CheckRedirect` calls, body slurping), and
   `http.Client`'s own loop would still follow any 3xx it returned, so
   `CheckRedirect` would need a new `Config` field (an API change). A
   `NewTransport` user would still get Go's methods.
3. **Documentation only** ("set `CheckRedirect`, avoid PUT redirects"):
   not browser-exact by default (decision 0008's spirit).

The limit lives in the Transport for the same reason: with
`http.Client`'s default `CheckRedirect` a client of your own stops at 10,
before mimicry's 20; one that allows more still stops at 20.

## Not measured, or not explained

- **Same-origin PUT and DELETE in the profiles.** Safari's fetch kind
  list has no `Origin` slot, and no profile had a variant for a
  same-origin PUT/DELETE or a redirected one, so Safari refused those
  requests (`ErrNotMeasured`). kindsgen now reads the cors-edge capture
  (HeadersOrder's change: every first leg and the non-GET hops): Safari
  27 and 26 gained `{PUT, cors}`, `{DELETE, cors}` and their `redirected`
  forms, Chrome and Firefox the `redirected` ones. With them
  `TestCORSEdgeMatchesBrowser` passes for all four profiles.
- **Header order on the GET hops.** kindsgen leaves out the redirects'
  GET hops (`chain.so.hop<n>`, the 303 and POST hops,
  `acao-redirect.cs.hop1`): they share a variant condition with the kinds
  and cors pages' redirects but are ordered differently, so its merge
  refuses them. Chrome places `origin` right after `accept` on
  `acao-redirect.cs.hop1`, after `sec-fetch-storage-access` on the kinds
  page's `fetch-redirect.so-cs.hop` (an Origin carried from the first leg
  vs. one added at the redirect, it seems); Safari orders each hop's
  headers its own way (`m-put-301.so.hop1` puts `sec-fetch-site`,
  `origin`, `content-length`, `priority` early, differently in 27 and 26)
  and drops `accept-language` and `priority` on the cross-site
  `acao-redirect.cs.hop1`; Firefox moves `referer` after `content-length`
  on the PUT hop and `origin` before `referer` on the cross-site hop. All
  identical across samples. The new test compares method, path, body
  length and `Origin`, not order; modelling these needs a variant
  condition split (did the first leg carry `Origin`?), a design decision.
- **307 and 308** were not in this capture (the `cors` capture's 307 was a
  GET): they keep method and body by the Fetch standard and Go alike.
- **Other methods** (PATCH, OPTIONS) and **HEAD** redirects: the
  standard's rule, not captured.
- **XHR** and elements in CORS mode (`crossorigin`): XHR takes the
  redirect CORS check and the Origin rule as fetch() does, unmeasured;
  elements are not checked.
- **Navigations**: the 20-redirect limit and the method rules apply to
  them too, from the Fetch standard; a form POST answered 302 sends its GET
  without `Origin` in every profile (Safari's `keep` is measured on fetch()
  only).
- **Credentials and wildcards** in the redirect check (`*` with
  `credentials: "include"`, `Access-Control-Allow-Credentials`): the Fetch
  standard's rules, shared with the preflight check, not captured.
- **Tainted origins** on redirects (a chain through a third origin):
  `Origin: null` as before; what Safari's `keep` does there is not
  captured.

## Follow-ups

- A variant condition for redirect hops whose first leg carried `Origin`
  (or another split) so kindsgen can take the cors-edge GET hops' orders,
  then a header-order comparison in `TestCORSEdgeMatchesBrowser`.
- A decision record for redirect ownership (the Transport corrects
  `http.Client`'s hops; the 20-redirect limit lives in the Transport;
  `NewClient`'s pass-through `CheckRedirect`), and an amendment to
  decision 0017 (a redirect's CORS check, `CORSError.Redirect`).
- Captures to close the gaps: a form POST navigation answered 302 (Origin
  on the GET, Safari), a navigation chain of 25 redirects, an XHR and an
  `<img crossorigin>` redirected without `Access-Control-Allow-Origin`, a
  cross-origin redirect chain with `credentials: "include"`.
