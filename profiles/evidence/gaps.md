# Not covered by any claim

Known differences from the browsers, and behaviour no capture measured,
with no work planned. Each line says when it shows, how likely a vendor is
to see it (detection), and what closing it would take. By
[decision 0029](../../docs/decisions/0029-scope-what-gets-modelled.md), one
is closed when a vendor is seen checking it or a caller notices it; open
work is tracked as [GitHub issues](https://github.com/roachadam/mimicry/issues).
A difference closed is removed here, with its pinned gap entry.

**TLS and below**

- **TCP/IP fingerprint** (all): the SYN is the host OS's (or the proxy's); detection high when the OS differs from the profile's, none on it; not planned ([0029, amendment](../../docs/decisions/0029-scope-what-gets-modelled.md#amendment-2026-10-30-the-tcpip-fingerprint)).
- **Real ECH in profiles without an `ech` capture** (`chrome-155-macos`, `chrome-156-macos`, `chrome-156-windows`, Firefox 158, Safari 26, the iPhone profiles): no `tls.realEch`, so no HTTPS lookup and GREASE ECH everywhere, where Chrome and Firefox of later versions send real ECH to a host publishing a config (Chrome 157 on Windows was not captured: no `chrome-157-windows` profile); detection medium for the Chrome and Firefox ones on such hosts, none where the browser ignores configs as Safari 27 does; an `ech` capture of each.
- **ECH on WebSocket and proxy connections** (Chrome, Firefox): a WebSocket's own HTTP/1.1 connection (`tls.websocketH1`), the TLS to an `https://` proxy, and every connection through a proxy keep GREASE ECH and look nothing up; no capture shows what the browsers do there; detection low to medium (only a host publishing a config can tell); `ech` captures of a WebSocket and through each proxy kind ([0068](../../docs/decisions/0068-real-ech.md)).
- **Whether the browser sees the record** (Chrome): Chrome on macOS resolving through getaddrinfo (with a scoped resolver, `/etc/resolver/test`) asked for no HTTPS record and sent GREASE; with secure DNS it asked and sent ECH, which is what mimicry always does; a user's Chrome may take either path by its DNS settings; detection low; captures of Chrome's default DNS path on each platform.
- **DNS queries around ECH** (Chrome, Firefox, Safari): mimicry asks HTTPS beside Go's A and AAAA, in plain DNS to the system's nameservers (or `Config.Resolver`'s `Dial`); Chrome asked A and HTTPS (no AAAA) and Firefox HTTPS and A (IPv6 off in the harness), both over DoH in the captures but Firefox on macOS; Safari asks HTTPS, A and AAAA, where a Safari profile asks no HTTPS; detection none at the server, only the resolver sees the queries; not planned.
- **Firefox's resumed GREASE ECH size** (Firefox): fixed at 400 bytes (432 over QUIC), measured against one ticket size; detection low; a `resume` capture with other ticket sizes ([report](../../internal/harness/reports/hello-record-2026-10-24.md)).
- **Firefox's next connection after ECH retry configs** (Firefox): each profile records what its own `ech` capture showed in every sample (`firefox-159-macos`, the system's resolver: the DNS config offered again, without the session; `firefox-159-windows` and `firefox-159-linux`, Firefox's own DoH: no ECH, the retry connection's session resumed with GREASE ECH and the real server_name, `tls.realEch.retryPlain`), but an uncommitted trial on macOS through Firefox's own DoH showed both in one run (the latter in 1 of 3 samples), so Firefox picks between them by something the captures do not show; detection low; more `ech` samples per platform and resolver.
- **A WebSocket's full hello** (Chrome, Firefox): `tls.websocketH1` captured resumed only; first socket with no ticket; detection low; a `websocket` capture on a fresh host.
- **HelloRetryRequest cookie position** (Windows, iOS, Chrome 155, Safari 26; every QUIC hello): the uTLS fork places it at random among the extensions that are not pinned; detection low; an `hrr` capture on each machine, and a QUIC server sending a HelloRetryRequest with a cookie.
- **Resumption forms** (all): TCP 0-RTT, several tickets at once, session-ID resumption never captured; mimicry uses one single-use ticket per key; detection low; `resume` captures.
- **TLS 1.2 ticket lifetime** (Chrome, Firefox): used until the certificate expires; long TLS 1.2 sessions; detection low; a long `resume-tls12` capture.
- **Resumed hello record version** (all): assumed 0x0301, not compared; detection none; add it to the resumed-hello diff.
- **Client certificates from Safari** (Safari, every iPhone profile): not capturable: Safari 27 sent an empty Certificate holding the identity in a temporary keychain, and stalled with it in the login keychain (2026-11-08); nothing installs an identity on the iPhone; no `tls.clientAuth`, so a certificate is `ErrNotMeasured`; detection none (refused); a way to give Safari an identity without a prompt ([0064](../../docs/decisions/0064-client-certificates.md)).
- **Client certificates over QUIC** (all): no browser was captured answering a CertificateRequest over QUIC; with `GetClientCertificate` set, a server asking over HTTP/3 sends the request, and the origin's later ones, over TCP, where the certificate is sent as measured (not counted as a QUIC failure); detection low (a browser might answer over QUIC); an h3 client-certificate capture.
- **A CertificateRequest not allowing the browser's scheme** (Chrome, Edge, Brave, Firefox): what a browser does when the server's `signature_algorithms` leave out the scheme it signs the key with is not captured; mimicry fails the request with `ErrNotMeasured`; detection none (refused); a capture server sending a narrower list.
- **Coalescing onto a connection with a client certificate** (Chrome, Edge, Brave, Firefox): not captured (no scenario has two hosts on one certificate); mimicry never coalesces onto a connection that sent a certificate or resumed a session that did, as Chrome's and Firefox's source say they do not; detection low; a client-certificate scenario with two hosts on one certificate.
- **Firefox's speculative connections to a server asking for a certificate** (Firefox): connections that carry no request, some dropped at the CertificateRequest, some answering it with an empty Certificate (55 and 115 over 36 samples, no pattern across samples); mimicry makes none; detection low (a connection count); not planned, as Chrome's preconnect ([0023, amendment](../../docs/decisions/0023-connection-limits-and-coalescing.md#amendment-2026-10-30-no-preconnects); pinned in `clientCertSpeculative`).
- **Chrome's preconnect meeting a CertificateRequest** (Chrome): dropped like the request's first connection, so Chrome drops two connections to the page's host where mimicry drops one; see Chrome's preconnect below (pinned in `clientCertPreconnects`).
- **Client key types** (Chrome, Edge, Brave, Firefox): only ECDSA P-256 and RSA-2048 identities were captured; any other key (P-384, P-521, Ed25519) is `ErrNotMeasured`, and RSA of another size is assumed to sign as RSA-2048 does; detection none for refused keys; a scenario per key type.
- **Client certificate chains** (Chrome, Edge, Brave, Firefox): every browser sent its identity's leaf alone, but none held an identity with intermediates, so what a browser sends then is not measured; mimicry sends the chain the caller gives; detection low; a capture with an intermediate CA.
- **No client identity** (Chrome, Edge, Brave): whether Chrome drops the first connection when it holds no identity to send is not captured; without `GetClientCertificate` mimicry answers on the first connection with an empty Certificate; detection low; a client-certificate scenario with no identity installed.
- **Parallel HTTP/1.1 connections resumed with a client certificate** (Brave on Windows): on `client-cert-ec` Brave resumed 3 of its 5 HTTP/1.1 connections to `h1.kinds-a.test` in 3 of 3 samples, where mimicry resumed 2 (as Brave on macOS, 6 of 6): how many open before the first one's ticket arrives is timing, which no field holds; detection low; none planned (`clientCertH1Resumes`).

**HTTP/1.1**

- **HTTPS upgrades and HSTS** (Safari, Chrome): by [decision 0016](../../docs/decisions/0016-literal-urls-no-https-upgrade.md) requests go to the URL given, with no TLS attempt first; detection low to medium; captures on ports 80 and 443, then an opt-in option ([report](../../internal/harness/reports/plain-http-2026-10-24.md)).
- **`Cookie` on a non-secure origin** (all): its slot in plain-HTTP lists is not measured; detection medium on plain-HTTP targets; a `kinds-plain` run with cookies.
- **Idle close** (all): 90 s on every protocol; how and when browsers close an idle connection is not captured (longest gap 35 s); detection low; a long idle capture ([0040](../../docs/decisions/0040-idle-connection-cleanup.md)).

**HTTP/2**

- **Chrome 155's opening records** (Chrome 155): from Chrome for Testing, not branded Chrome; detection none expected; a branded `resume` capture.
- **A connection opened before its request** (Safari, Firefox; Chrome on iOS): a page opened from outside a tab (a typed URL, a bookmark) has its first connection opened before the request exists, so the browser sends the opening alone, acknowledges the server's SETTINGS, and sends HEADERS 7–412 ms later (Safari 27 macOS 174 of 185 such connections, Safari 26 macOS 154 of 161, Firefox macOS 192 of 212; Firefox on Windows, Safari and Chrome on iOS 32–67%, varying between samples of one page); every other connection (1038 of 1047 for Safari 27 macOS) sends HEADERS at once and ACKs after, as mimicry always does. mimicry has the request when it connects, so even a typed navigation sends HEADERS first; detection low to medium (a typed navigation's first connection); not planned, intentionally ([0042, amendments](../../docs/decisions/0042-http2-opening-records.md#amendment-2026-11-04-counted-and-kept-not-planned), [#80](https://github.com/roachadam/mimicry/issues/80)).
- **Chrome on Windows's ACK in the same millisecond** (Chrome on Windows): on 953 of 1552 connections after a page's first, the SETTINGS ACK went before the first HEADERS within the same millisecond over loopback, a scheduling race a local capture cannot settle for real paths; mimicry sends HEADERS first; detection low; real-network captures.
- **Chrome's re-prioritisation** (Chrome): a PRIORITY frame mid-load, and a mid-upload stream kept in its lists ([INFERENCE]); never sent; detection medium; model `OnStreamUpdate` against the page traces.
- **Several requests in the opening record** (Safari on iOS): with three requests waiting as a connection opened, the iPhone put all three HEADERS in the opening's TLS record; `http2.openingRecords` describes the first request's only; detection low; a capture with requests of known count waiting, and a record rule for them.
- **Upload of unknown length** (all): ends with an empty END_STREAM DATA frame; streamed bodies; detection low to medium; a streaming-upload capture.
- **Idle origin moved to new TCP** (Chrome on macOS and Linux, Edge, Brave): after a broken HTTP/3 origin, a new TCP connection after 6–10 s idle (Linux: 8.0 s, 3 of 3 samples; Edge: 8.0 s, and again after 10.0 s, 3 of 3; Brave: one new connection, 3 of 3 on macOS, Windows and Linux); detection low; captures to find the cause ([`h3EdgeGaps`](../../internal/harness/e2e/http3_edge_test.go)).
- **Brave on Linux's early second connection** (Brave on Linux): in 1 of 3 `h3-broken` samples Brave opened a second, resumed TCP connection to the page's second host 4.0 s after its first, which carried nothing until the page's next request to that host 35 s later; mimicry opens none; detection low; more samples (h3gen's `hold`, `braveLinuxBrokenVaries`).
- **Upload DATA chunking** (all; Firefox entirely): 65535-byte chunks match only the first chunk; uploads over 64 KiB; detection low; upload captures of several sizes.
- **Blob and File bodies joined with the head** (Chrome): Chrome sends a Blob or File body apart from its head even when the two fit 1400 bytes (`http1-upload`'s `/up/blob-100`, `-500`); mimicry cannot tell a Blob from bytes and joins every small body up to `http1.uploadRecords.joinUpTo`; small file uploads over HTTP/1.1; detection low; none planned (decision 0052).
- **Chunked HTTP/1.1 request bodies** (all): no browser sends one from a page (Chrome and Safari refuse a ReadableStream body over HTTP/1.1, Firefox sends its string form); mimicry's chunked body, which a caller asks for with an unknown length, goes out with its head as one stream in 16 KiB writes; detection low; none planned (decision 0052).
- **HTTP/2 upload records** (all): browsers' upload records follow their DATA frames and flow control (`h2-upload`), which mimicry's HTTP/2 writer was not compared against record by record; large HTTP/2 uploads; detection low; an e2e comparison of `h2-upload`'s records.
- **Credit return timing** (Firefox, Safari): returned at the profile's threshold, not paced by reads; large downloads; detection low; a read-paced model. Firefox's largest `/big` stream increment was 3.56 MB in 3 samples on Windows and 3.16 MB on Linux, below mimicry's 4 MiB step, which 2 of 3 macOS samples sent (`creditGaps`).
- **REFUSED_STREAM** (Safari, iOS profiles, Chrome 155): unmeasured, so a refused stream retires the connection and the request goes on a new one, where Chrome 156 and Firefox 158 resend on the same (`http2.refusedStreamSends`); a refused extended CONNECT (HTTP/2 WebSocket) opens the socket on a connection of its own in every profile; detection low; a refusing scenario.
- **Error-path frame order** (Chrome): RST_STREAM before discarded credit, GOAWAY before close ([INFERENCE]); not checked; detection low; error injection.

**QUIC and HTTP/3**

- **HTTP/3 and ECH from DNS HTTPS records** (all; ECH over QUIC: Chrome, Firefox): records are looked up for their ECH configs only, and only by profiles with `tls.realEch` ([0068](../../docs/decisions/0068-real-ech.md)); their `alpn` is never used, so a site whose record names `h3` is reached over TCP until `Alt-Svc` moves it (for an ECH host, where `altSvcIgnored` holds, never), and no QUIC hello carries real ECH, only GREASE. Uncommitted `ech-h3` trials (a record with alpn `h3,h2` and an ECH config, QUIC on UDP 443) sent Chrome 157 and Firefox 159 straight to QUIC with real ECH (outer `server_name` the public name), as such a record would in the wild (`cloudflare-ech.com`'s, 2026-11-10: alpn `h3,h2` and `ech`); mimicry stays on TCP with ECH there; detection medium; HTTP/3 discovery from records, and `quictrace` finding the keys of an ECH-accepted QUIC connection to capture its inner hello ([report](../../internal/harness/reports/http3-2026-10-25.md)).
- **`Alt-Svc` on ECH connections where not measured** (Chrome on Linux, Edge, Brave, Firefox on Windows and Linux): `realEch.altSvcIgnored` comes from `ech-h3`, captured on macOS only, so these profiles move a host whose ECH config they use to HTTP/3 (with GREASE ECH) after its `Alt-Svc`, where Chrome and Firefox on macOS stayed on TCP with ECH; detection medium; an `ech-h3` capture on each machine.
- **A returning browser's first request** (all; Firefox most): a saved alternative starts like any known one; no browser captured restarting; detection low; restart captures.
- **Dead-path waits** (Firefox, Safari): a sent request on a silent path waits as the browser's does (30 s, 12 s); detection none; a dead-path signal and a resend rule.
- **Safari's other kinds** (Safari): only `fetch()` measured over HTTP/3, so other kinds stay on TCP; also its QPACK table, PRIORITY_UPDATE, bodies, close reply; detection medium; a fuller `h3-page` capture.
- **Firefox's declined TCP beside a 425** (Firefox): it opens and drops a TCP connection on most 425 retries; detection low; more samples ([`h3EdgeGaps`](../../internal/harness/e2e/http3_edge_test.go)).
- **When Firefox's held request leaves** (Firefox): with its Finished in 31 of 35, after it in 4; mimicry always with it; detection low; thread timing, nothing likely (`sampleGaps`).
- **Safari's OPTIONS fetch** (Safari): not in its kinds captures, so refused (`ErrNotMeasured`); detection low; an OPTIONS fetch on the kinds page ([`h3EdgeGaps`](../../internal/harness/e2e/http3_edge_test.go)).
- **Safari on iOS's beacon over HTTP/3** (Safari 27 on iOS): the iPhone sent `h3-page`'s beacon on a QUIC connection of its own beside the page's HTTP/2 one (3 of 3; Safari 26 on the iPhone kept the page on TCP, as on macOS); mimicry keeps it on TCP, Safari's kinds being measured over HTTP/3 for `fetch()` only; detection low; a fuller `h3-page` capture (`h3Gaps`).
- **Safari on iOS's QUIC failure rules** (Safari on iOS): for Safari 27, fallback, keep-alive, acknowledgement and credit copied from Safari 27 on macOS (**C**), loss, key update, 0-RTT, dial delays and close on GOAWAY not measured; for Safari 26, the failure pair's structure measured (**W**: keep-alive, path degrading, close on GOAWAY, the fallback's mode), its timing, acknowledgement and credit copied from Safari 26 on macOS (**C**), the rest of loss, key update, 0-RTT and dial delays not measured; the iPhone's second Initial pair in a blackholed attempt and its unpadded Initials (1038 and 1129 bytes) not imitated (the stack's defaults, no 0-RTT); detection low; the failure pair's timing over a wired path, and an iPhone `h3-early` capture.
- **Chrome and Firefox on iOS's extra Initial probes** (Chrome and Firefox on iOS): in a blackholed QUIC attempt the iPhone's Chrome sent one or two retransmitted Initial pairs (a 1038-byte unpadded datagram and a 1200-byte one) 28–137 ms in, before or as the raced TCP connection opened, 6 of 6 attempts (the "6 Initials"; Safari 26 on the iPhone: none or one pair); Firefox on the iPhone the same in both blackholed attempts, and once in `h3-page` when the server's first flight came late (`h3Gaps`); mimicry's attempt probes as its QUIC stack does; detection low; the iPhone's loss rules over a wired path.
- **When an abandoned attempt stops** (Safari; Chrome and Firefox on iOS): the browser drops its QUIC attempt once the request is on the TCP connection. Safari on macOS sends its 0-RTT close 8–11 ms after its TCP ClientHello and 0–2 ms after the request reached the server (6 of 6). Chrome on the iPhone sent an Initial pair 0–8 ms after the ClientHello in 3 of 6 blackholed attempts. mimicry drops the attempt as the request leaves for TCP, before its dial (`internal/engine/native`: `await`, `roundTripEarly`), so its 0-RTT close goes out before its TCP ClientHello and it probes no later than the race delay. Detection low. Closing it means dropping the attempt on the TCP connection's first request ([0028, amendment](../../docs/decisions/0028-quic-failure-model.md#amendment-2026-11-03-what-counts-as-an-abandoned-attempt)).
- **Chrome's insecure-form warning** (Chrome on iOS): before submitting a form over plain HTTP Chrome asks ("Send anyway"), Safari does not; behaviour on the screen, not on the wire, so not modelled; `kinds-plain` on the iPhone needs someone to tap it (docs/capturing.md); detection none.
- **Firefox on iOS's HTTP/1.1-only ALPN** (Firefox on iOS): in two three-sample `http1` runs the capture tool's log showed sample 1's ClientHello offering ALPN `http/1.1` alone and sample 3's `h2, http/1.1`, in both runs; no rule found (the committed `http1` samples are single-sample runs, and its trace keeps the HTTP/1.1 requests, not the ClientHello's ALPN, so no test can check it); not imitated; detection low; an `http1` capture that records the ALPN per sample.
- **Firefox on iOS's redirect stall** (Firefox on iOS): about one `redirects2` or `redirects2-cookies` sample in three stalled after the "too many redirects" page, even with Firefox restarted before each sample, and never opened the next URL; behaviour on the screen, not on the wire, so not modelled; the samples were taken as single-sample runs (docs/capturing.md); detection none.
- **Safari's close on GOAWAY with requests open** (Safari): every captured GOAWAY found no request open, and Safari closed at once; with requests open mimicry waits for them, then closes (an assumption, decision 0050); detection low; a GOAWAY that leaves a request in flight.
- **Safari's pair on a 0-RTT connection** (Safari): with a GET and a POST made together, Safari sent the control stream alone, then the GET (6 of 6); mimicry sends the GET in the control stream's packet, as for a lone GET (`earlyStreamsWithRequest`); detection low; more samples to say what decides it.
- **Chrome 156 Windows's GREASE transport parameter** (Chrome on Windows): 3 resumed hellos of its edge captures carry a 15-byte one, beyond the profile's 14, which the `h3-discovery` and `h3-page` connections set; detection low; derive the maximum from the edge captures too (h3gen reads them for resumed first flights only where the h3 captures have none).
- **Chrome's packet numbers in some resumed first flights** (Chrome): in some edge resumed attempts (`h3-broken` sample 1 connection 3, `h3-early` sample 1 connection 2) the 0-RTT packets do not continue the shared numbering the `h3-discovery` connections follow; not checked (as the GREASE line); detection low; a look at those flights.
- **nginx drops Chrome's port migration** (Chrome): nginx answers nothing on the new path, so a 30 s stall; mimicry migrates as Chrome; detection none; a capture of Chrome doing it.
- **Chrome after declining to move** (Chrome): a server's `disable_active_migration` keeps Chrome on its degrading path ([Chromium source](https://chromium.googlesource.com/chromium/src/+/refs/tags/156.0.8078.85/net/quic/quic_chromium_client_session.cc#3282), a lead; [RFC 9000 §18.2](https://www.rfc-editor.org/rfc/rfc9000#section-18.2)), and mimicry stays with its keep-alives, probes and idle timeout; what Chrome does then (probes, close timing, where the stuck request goes) is not captured; detection low; a Chrome `h3-broken` capture against a server sending the parameter.
- **Chrome's blackhole close** (Chrome, Edge, Brave): Chrome closes after 54–61 s and resends on TCP (Edge and Brave 54.4–54.5 s, macOS and Windows, Brave on Linux too); mimicry falls back at 30 s; detection low; not planned ([0028, amendment](../../docs/decisions/0028-quic-failure-model.md#amendment-2026-10-30-blackhole-detection-and-resumed-probes)).
- **Edge on Windows's early path move** (Edge on Windows): in 1 of 3 `h3-broken` samples Edge moved its silenced connection to a new path after 2.91 of its PTOs, 13 ms after its second probe, where the others and every other Chromium sample moved after about 4; mimicry moves after 4 (`afterPtos`); detection low; more Windows samples, to tell a rule from a timer (`pathMoveGaps`).
- **Brave's path move timing** (Brave, macOS and Windows): Brave moved its silenced connection 3.3–3.9 of its PTOs after its last request by the e2e test's measure (macOS 3.41, 3.48, 3.72; Windows 3.29, 3.87, 3.89), always after its second probe; mimicry moves after 4 (`afterPtos`, as Chrome's; 3 would race the second probe, [0067, amendment](../../docs/decisions/0067-brave-profiles.md#amendment-2026-11-16-braves-path-move-after-4-ptos-as-chromes)), so the earlier moves differ by about 20–25 ms; detection low; more samples, to tell a rule from a timer (`pathMoveGaps`).
- **Resumed attempts' probes** (Chrome, Firefox): Chrome's 4 Initials and lone 0-RTT datagrams, Firefox's varied probes; only to a silent server; detection low; not planned (same amendment).
- **Firefox's short-lived QUIC side connections** (Firefox, macOS, Windows and Linux): Firefox intermittently opens QUIC connections beside the page's that carry no request and closes each 1–5 ms after its handshake, H3_NO_ERROR: Firefox 158 on Windows in 2 of its 36 HTTP/3 page samples (`h3-broken`, `h3-download`, one per request: 14 and 7); Firefox 159 in 3 of 6 macOS and 4 of 6 Windows `h3-discovery`/`h3-page` samples with locally trusted roots (8–20 per sample, about 300 ms apart), after which later connections to the host in the sample resume nothing and carry no token, and the server's close in `h3-discovery` got no TCP race; on Linux in about half of the `h3-*` samples (15 per sample) and in every `h3-streams-blocked` sample (6, each within 4 ms of a fetch), and in those samples no GET or HEAD went in 0-RTT and the resumed attempt after the server's close ended silently; mimicry opens none; trigger unknown; detection low; more samples to find when (h3gen's `sampleGaps`, kindsgen's `h3AltUsedGaps`, `h3EdgeGaps`).
- **Firefox on Windows's resumed attempt** (Firefox on Windows): after the server's close, its resumed attempt first probed 1.7–1.9 s after its first flight (`cachedRtt` false) and gave up at 9.8 s or 10.2 s, or (1 of 3 samples) probed from a cached RTT and ended silently at 4.5 s with nothing held (6 further samples: 9.8, 9.8, 10.2, 10.3, 5.0 s and one silent end); mimicry gives up at 9.8 s; only to a silent server; detection low; more samples to find what decides (h3gen's `sampleGaps`).
- **Firefox on Windows's late timers** (Firefox on Windows): its keep-alive PING came 15.00–15.39 s after its idle timer restarted, 4 of 9 samples more than 50 ms late, and requests waiting on a silenced connection moved to TCP 73–470 ms after the server's idle record (macOS 7–22 ms); mimicry's timers fire on time; detection none; nothing likely (h3gen's `sampleGaps`).
- **How long an origin stays broken** (all): for the Transport's life; Chrome's source backs off 5 min; detection low to medium; a multi-page, minutes-long capture.
- **Locally trusted roots** (Chrome, Firefox): HTTP/3 captured with QUIC forced; a public root may race differently; detection unknown; a capture with a public certificate.
- **HTTP/3 lists with cookies** (all): no cookie went over HTTP/3, so its slot (and Firefox's `alt-used` beside it) is assumed; detection medium; `h3-page` with cookies.
- **Firefox's `alt-used` on credential-less requests** (Firefox): its source omits it there; never compared; detection low; those kinds in `h3-page`.
- **Safari's handshake loss timing** (Safari): probes and give-up are the stack's defaults; heavy loss; detection low; a capture with QUIC blackholed and no TCP ([report](../../internal/harness/reports/quic-interop-2026-10-25.md)).
- **Firefox's v2 resumption against old lsquic** (Firefox): lsquic's v1-typed Retry stalls it until TCP; real Firefox there not captured; detection low.
- **Server bugs browsers hit too** (Chrome): lsquic before 4.10, nghttp3's PRIORITY_UPDATE limit, kwik on 0-RTT; as in Chrome; detection none. One unexplained close by www.akamai.com (Safari 26), not reproduced.
- **Retry** (all): no browser captured answering a Retry; detection low to medium; a Retry-forcing server.
- **PMTU probing, ECN, DATAGRAM, ACK_FREQUENCY** (all): not done or ignored; not measured; real paths; detection low to medium; real-network captures.
- **Server QPACK dynamic table** (all): the decoder side is not measured; detection low to medium; such a server.
- **A navigation's 0-RTT** (Chrome, Edge): on a resumed connection Chrome and Edge held a navigation (GET) until after the Finished, 3 of 3 `h3-resume-table` samples each, where their fetch, XHR and image GETs went in 0-RTT; `http3.earlyData` holds methods only, so mimicry sends the navigation in 0-RTT; detection low; a navigation rule in `http3.earlyData` (`h3EdgeGaps`).
- **Chrome's NEW_TOKEN cache** (Chrome): Chrome often omits a token it has (3 of 9); mimicry always presents it; detection low; token-cache captures (`sampleGaps`).
- **Edge's second Initial in 1 byte** (Edge and Brave): 8 of 123 connections on macOS and 9 of 123 on Windows sent the second Initial's packet number in 1 byte (Brave: 7 of 150 on macOS, 12 of 150 on Windows, 8 of 156 on Linux), all with a token, against `shared_second_long`'s 2; nothing on the wire tells them apart (scenario, timing, `initial_rtt`, hello size); mimicry always sends 2; detection low; more captures, or Edge's field trials (h3gen's `sampleGaps`, `h3Gaps`).
- **Brave's late Initial ACK out of order** (Brave on macOS): the one connection of 21 that acknowledged the server's Initial sent that Initial packet after the Handshake and 1-RTT packets it led; mimicry never acknowledges an Initial (`ackInitial` false); detection low (h3gen's `coalescedOrder` pin).
- **Chrome's late PRIORITY_UPDATE** (Chrome 156 and 157, Brave on Windows and Linux): sometimes 1 ms after HEADERS under load; mimicry sends it first; detection low; more samples (`sampleGaps`).
- **`h3-early` POST on Windows** (Chrome and Firefox on Windows): the replay makes both requests at once, so mimicry's POST is held; detection none; replay at the browser's issue times (`h3EdgeSchedulingGaps`).
- **Chrome's TCP delay from the smoothed RTT** (Chrome): 1.5 × RTT, invisible on loopback; detection low; a real-network capture.
- **Migration by Firefox and Safari** (Firefox, Safari): never seen, never done; NAT rebinding; detection low; a rebinding capture.
- **Long and slow transfers** (all): key updates past 37,000 packets and credit past 50 MiB not measured; no client key update; detection low; longer captures.
- **Safari's connection credit across lost data** (Safari): its MAX_DATA is what arrived plus the stream window (`quic.credit.connectionStreamWindow`), but no `h3-download` sample lost a packet (none of its about 37,000 server data packets went unacknowledged), so whether data beyond a gap counts before the gap is resent is not measured; mimicry counts the largest offset received, as RFC 9000's flow control does, so with loss its raises run ahead of what it acknowledged by the gap (the download test's `lostData`); detection low; a download capture with loss.
- **Keep-alive with a short server idle timeout** (all): PINGs at half of it; detection low; a short-idle capture.
- **`requestsAfterConfirmed` on full handshakes** (Chrome, Firefox): the rule is false from the requests held out of 0-RTT, which leave before the handshake is confirmed; no request waited for a full handshake, so whether one ready during it waits is not captured; detection low; an immediate-request scenario.
- **Firefox v2 edges** (Firefox): a v2 connection's NEW_TOKEN not passed on; a v2-only server sending `version_information` untested; the resumed hello's SNI cut varies; detection low; more samples.
- **QUIC stack gaps** (all): the server's `preferred_address` is not used, its `max_udp_payload_size` not acted on; detection low ([UPSTREAM.md](../../internal/quic/UPSTREAM.md)).
- **STREAMS_BLOCKED where not captured** (Chrome 155, Chrome 156 on Windows, Safari 26): no `h3-streams-blocked` capture (`missingCaptures`), and none can inherit another's (decision 0035: from an older version of the same browser and platform only), so `quic.streamsBlocked` is not measured and they send none; only against servers allowing few streams; detection low; the capture on the Windows PC and the macOS 26 Mac.
- **Firefox's spacing of requests made together** (Firefox, macOS, Windows and Linux): a burst of fetches a page makes together leaves 3.2–5.7 ms apart (macOS; Windows 3.7–5.2, Linux 3–14), each request in its own packet; mimicry sends requests made together as they come, the first two of an `h3-streams-blocked` burst in one packet. Against quic-go, which raises its stream limit per stream acknowledged, the server then answers both in one packet and raises by two, and mimicry sends one STREAMS_BLOCKED per two waiting streams (7, 13) where Firefox sends one per stream (6 7 8, 12 13 14; on Linux 2 of 3 samples sent the second burst's two waiting streams in one packet behind 13); with the requests 5 ms apart mimicry sends Firefox's (tried 2026-11-02); whether the spacing is the page's script or Firefox's network code is not measured; detection low ([`h3EdgeGaps`](../../internal/harness/e2e/http3_edge_test.go)).
- **Chrome's small-packet padding** (Chrome): Chrome's 29-byte 1-RTT packets (a lone PING, RETIRE_CONNECTION_ID or STREAMS_BLOCKED) carry their PADDING before the frame; mimicry's STREAMS_BLOCKED packet is the same 29 bytes with it after (upstream's header-protection minimum; its other small packets likewise, [INFERENCE]); seen only by the server, after decryption; detection low; where Chrome pads, from its small packets.
- **Opaque transport parameters** (Firefox, Safari 26, Safari on iOS): `0x1d` and `0xff080808` sent verbatim, meaning unknown; Safari 27 on macOS stopped sending the latter, Safari 27.2 on iOS sends it (= 9, last); detection none; source research.

**Request headers and kinds**

- **Page header order** (all; XHR, Firefox's object-literal `fetch()`): name order, not the page's; detection medium; `Request.HeaderPlacement` by hand, no new API ([0021, amendment](../../docs/decisions/0021-page-headers-hash-table-order.md#amendment-2026-10-30-no-api-for-the-pages-header-order)).
- **Safari's common names** (Safari): page-set `Authorization`, `Cache-Control` may enter its hash table among its own; only `content-type` captured; detection medium; a `headers-order` capture.
- **Safari on iOS's large page-set header sets** (Safari on iOS): with 26 or more page-set names its order is not CFNetwork's table as modelled, and its XHR puts a name set twice elsewhere; mimicry orders them as on macOS; detection low (`headersGaps` in kindsgen, `headersOrderGaps`).
- **Chrome's `content-type` role** (Chrome): page header or its own, unresolved; Blink's source followed; detection low to medium; a `headers-order` capture.
- **Requests from a cross-site frame** (all): their top-level site, headers and preflights are not modelled; detection medium; a frame capture and an API. Brave farbles their `Accept-Language` by its tab's page; mimicry by `Request.From`, the frame's origin.
- **Brave's blocking lists** (Brave): Shields refuse requests to listed ads and trackers before they leave; mimicry sends every request it is asked for (no capture page uses a listed URL); detection low (a blocked request never reaches a server); not planned.
- **`Sec-Fetch-User` on frames and HTTP/1.1** (Chrome, Firefox): either accepted on frames; Firefox's clicked form POST over HTTP/1.1 refused; detection medium; a clicked form on `kinds-http1`.
- **Pages below `/`** (all): the full-path `Referer` follows the standard, not a capture; detection medium if wrong; a deep kinds page.
- **A lone `%` in a path** (all): browsers send it as written (`urls`, `p-lonepct`); Go's `url.Parse` refuses the URL, so `http.NewRequest` fails before mimicry sees it; a caller can send it with `req.URL.Opaque`, which mimicry sends as written (decision 0057); detection none (mimicry sends nothing otherwise) (`urlsKnown`).
- **Pooling a host ending in a dot** (Chrome, Edge, Firefox): Chrome sends a fetch() of `host.` on `host`'s connection and opens a new one for a navigation; Firefox does the opposite; mimicry runs the case once and matches one of the two; detection low (hosts typed with a dot); top-level-site partitioning (Chrome, decisions 0011 and 0029) and Firefox's connection grouping (`urlsKnown`).
- **URL rules without a `urls` capture** (`chrome-155-macos`): branded Chrome 155 cannot be installed, and its testing build gives only the network stack's `tls.trailingDotSni`; a `\|` in a path or an invalid `xn--` label is `ErrNotMeasured`, every other URL as the browsers measured agree; detection none.
- **A host ending in a dot over HTTP/3** (all): the `urls` page is TCP only, so its SNI over QUIC follows `tls.trailingDotSni` by inference (each browser builds both hellos from the host); with `omit` (Safari) such a QUIC connection keeps no ticket, since uTLS keys QUIC tickets by server name, so it never resumes; detection low; an Alt-Svc case for a trailing-dot host.
- **IPv6 literals** (all): kept as written; the URL standard compresses them (`[0:0::1]` is `[::1]`); not captured (the capture server listens on IPv4 only); detection low; a `::1` listener and `ip6-*` cases.
- **`FontFace` loads and `crossorigin` stylesheets** (all): no kind; detection low to medium; add both to the kinds page.
- **Layout-driven image priorities** (Firefox, Chrome, Edge, Brave): layout changes them (`u=4`, `u=1`); detection low (`redirectsLineGaps`, `h3Gaps`, `h3PriorityGaps`).
- **Safari 26's font cookie race** (Safari 26): it sent a font before a cookie was set; detection none (`raceCookieLabels`).
- **Edges from source only** (Safari, all): Safari's hash tables past 1732 names or for names over 96 characters; the navigation's `content-length` slot, which no request reaches; detection none.
- **Bodiless POST and PUT without a `bodiless` capture** (Chrome and Firefox on Windows, every iOS profile, `chrome-155-macos`, `safari-26-macos`): no `emptyBody`, so a POST or PUT with no body goes without `content-length: 0`, its stream ended on HEADERS. The `cors` captures already show every profile's cross-site fetch PUT with no body (`put.cs`, the `maxage.cs` PUT) sending `content-length: 0` (Chrome and Safari in the list's place with END_STREAM on HEADERS, Firefox last with an empty DATA frame); kindsgen does not read them for `emptyBody` yet, and POST is unmeasured there; detection medium; a `bodiless` capture per profile ([#56](https://github.com/roachadam/mimicry/issues/56)).
- **Safari's bodiless fetch() order** (Safari 27 macOS): its fetch() POST, PUT and PATCH without a body start `sec-fetch-site, accept, origin` (its header table without `content-type`); mimicry sends the order of its lists measured with a body, `accept, origin, sec-fetch-site`, as it did before; `content-length: 0` and the framing match; detection medium; the header table applied to Safari's own headers whenever the list's measured set differs (`bodilessGaps`).
- **`Width` and `Sec-CH-Width`** (Chrome, Edge): an `<img>` with `sizes` sends its layout width once the page's origin opted in (`client-hints`, `next.width-img`: 50px × DPR); mimicry has no way to say an image's width and sends neither; detection low (sizes images on opted-in sites); a request field for the width (`h3Gaps`, the `client-hints` header list of `/h3/next.width-img`).
- **`Clear-Site-Data` on a redirect** (Chrome): emptied like any other response's, not captured; detection low ([0055](../../docs/decisions/0055-client-hints-opt-in.md)).
- **Network client hints** (Chrome): `rtt` is mimicry's last TCP connect time (QUIC connections do not update it) and `downlink` the machine's captured estimate (1.6 Mbps; 1.55 on Linux), each with ±10% noise and fixed per host for the Transport's life, where Chrome's network quality estimator measures HTTP round trips and throughput and changes over time: on Linux it rose by 30% or more within one sample (1.3 and 1.75 Mbps to one host; kindsgen's `downlinkGaps`); detection low ([0055](../../docs/decisions/0055-client-hints-opt-in.md)).
- **Client hints opt-in without a capture** (`chrome-155-macos`): no `clientHints`, so `Accept-CH` is ignored as before; detection high on sites that opt in; a `client-hints` capture, which Chrome 155 can no longer give (not installable as branded Chrome).

**Cookies**

- **Safari's `Domain` cookies of two levels** (Safari): order a guess; shop cookies; detection low to medium; a `cookies-edge` step.
- **Limits and eviction** (all): no total limit; Chrome's priority and `Secure`-aware eviction not modelled; 180 → 150 from source; partitions counted apart; detection low; `cookies-edge` captures.
- **Unmeasured rules** (all): Chrome's 120 s Lax window end; `Expires` by the local clock; Safari refusing third-party cookies on store or send; Safari's partition against path length; `__Host-` from a deep path; loopback hosts other than `localhost`; Chrome and nameless `__Http-` values; detection low or none; a capture each, small.
- **WebSocket handshake cookies** (all): a `Strict` cookie on a cross-site socket, the host's partition cookie, `Set-Cookie` on the upgrade; detection low; a fuller `websocket` capture.

**CORS**

- **Preflight `Max-Age` caps** (all): honoured as sent; browsers cap it (2 h, 24 h, 10 min, by source); detection low to medium; a long session.
- **Safelist and refusal edges** (all): from the Fetch standard, not captures; detection low; a fuller `cors` page.
- **Preflight cache keys** (Chrome): keying by top-level site not measured; a hop's preflight over plain HTTP not tested; detection low; small captures.

**Redirects**

- **Safari 26's clicked navigations** (Safari 26): not captured; follow its script's; detection low (`missingCaptures`).
- **Chrome 155's hop `cookie` slot** (Chrome 155): no twin captures, so cookies go after the list; detection medium; ends with its deprecation.
- **`cookie` slot on hops no twin carried cookies on** (all): credentialed cross-site hops, hops from `http://`, Safari 27's same-site image hop; detection low to medium ([0048](../../docs/decisions/0048-cookie-twins.md)).
- **Chrome's error-page reload** (Chrome, Edge, Brave): reloads after the redirect limit; mimicry returns the error, by [decision 0022](../../docs/decisions/0022-redirects-as-the-browser-follows-them.md); detection low (`redirectsReload`).
- **Unmeasured chain rules** (all): `navigationSite` on longer chains; `hopPreflight` to another cross-site origin; CORS checks of style, font and preload redirects; Safari's `keep` Origin through a third origin; the frame redirect limit; detection low to medium; a `redirects2` step each.
- **Safari's cold first sample** (Safari): a hop on a new connection with another order; detection low (`sampleGaps` in kindsgen).

**WebSockets**

- **Firefox and an 8-bit window** (Firefox): Firefox hangs, mimicry fails the dial as Safari; detection none ([report](../../internal/harness/reports/websocket-deflate-2026-10-26.md)).
- **Firefox's transport end** (Firefox): Firefox 158 on macOS never ended one, so `firefox-158-macos` ends it 10 s after the close; on Windows and Linux, and with Firefox 159 on macOS, its HTTP/1.1 ones are modelled (`closeH1`), its HTTP/2 streams it left to the server but one: the cross-site socket on a connection of its own, which it reset with RST_STREAM CANCEL 1.0 s after the close (every sample, Firefox 159 on macOS and Linux too; `webSocketEndGaps`); detection low; a longer macOS capture, and a rule for which HTTP/2 sockets Firefox ends.
- **Chrome's stream end after a close** (Chrome): Chrome drops it after 2 s, mimicry resets after 10 s; servers that leave it open; detection low.
- **Chrome's fragmented large message** (Chrome): split in some samples, one frame in mimicry; detection low; more sizes.
- **Firefox's HTTP/2 DATA segmenting** (Firefox): the header counted into 16000 bytes, and flow-control cuts, not modelled; detection low.
- **`ws://` from an `https://` page** (Firefox, Safari): refused as the browser fails it; whether they try `wss://` first is only in the server's log; detection low.
- **Modelled, unexplained** (Firefox, Safari 26): Firefox's socket hello drops `compress_certificate`; Safari 26 sends a cross-site host's Lax and None cookies on cross-site sockets; detection none.
- **Safari's compression threshold** (Safari): between 6 and 4095 bytes, not measured; detection low.

**Connections**

- **No top-level-site partition** (all): a third-party host reached from two sites shares a connection, a cross-site socket may share its host's own, and a shared `AltSvcCache` spans sites; detection medium; one Transport per site ([0011](../../docs/decisions/0011-connection-partitioning.md)).
- **Chrome's preconnect** (Chrome): one more handshake to the page's host per page load (through a proxy, extra CONNECTs); detection low to medium; not planned ([0023, amendment](../../docs/decisions/0023-connection-limits-and-coalescing.md#amendment-2026-10-30-no-preconnects)).
- **Speculative and raced ECH connections** (Chrome on Linux, Firefox): in the `ech` captures Chrome on Linux opened a second connection to the page's host about 7 ms after the first in every sample, and Firefox over its DoH (Windows, Linux) one more too, each carrying no request; Firefox on macOS raced two connections with the config the server rejects in 1 of 3 samples (`echGaps`); mimicry opens neither (the e2e test leaves them out); detection low; not planned, as Chrome's preconnect ([0023, amendment](../../docs/decisions/0023-connection-limits-and-coalescing.md#amendment-2026-10-30-no-preconnects)).
- **Firefox on Windows's unused opening connection** (Firefox on Windows): a second TCP connection to the page's host 0–27 ms after the first, its HTTP/2 preface and GOAWAY, unused (131 of 135 page samples opened directly over HTTPS, none through a proxy); its handshake leaves Firefox one more TLS 1.2 ticket, so one more connection resumes (`resume-tls12`: 5/3 to the page's host, mimicry 5/2); detection low to medium; not planned, as Chrome's preconnect ([0023, amendment](../../docs/decisions/0023-connection-limits-and-coalescing.md#amendment-2026-11-01-firefox-on-windowss-unused-connection); `unusedOpenings`, `resumeCountGaps`).
- **Firefox's credential-less connections** (Firefox): their own connection to some hosts (every macOS sample, 2 of 3 on Windows, 1 of 3 on Linux), no rule found; detection low to medium (`partitionGaps`).
- **Safari on iOS's beacon connection** (Safari 27 on iOS): its beacon, cookies and all, goes on the credential-less connection; mimicry sends it on the credentialed one; detection low; a rule for which kinds share that pool (`partitionGaps`).
- **Tabs** (all): a Transport is one session; what tabs share is not measured; detection medium if misused ([0019](../../docs/decisions/0019-transport-is-one-browsing-entity.md)).
- **Coalescing conditions** (all): address, port, partition and proxy never varied, and mimicry never coalesces through a proxy; detection low to medium; a fuller `connections` capture.
- **Limits beyond the per-host cap** (all): the 6 per host applied to plain HTTP and per proxy route ([INFERENCE]); Chrome's 256 total and 32 per proxy, Firefox's 900, and priority queueing not modelled; detection low.
- **Connections per page** (all): not compared against the replays; extra unused connections in the WebSocket captures not analysed; detection low.

**Proxies**

- **Safari's `Proxy-Authorization` inside tunnels** (Safari): sent to servers once its credential state is on; mimicry never does; detection low; captures of the trigger and a decision on sending proxy credentials to servers ([report](../../internal/harness/reports/proxy-websocket-2026-10-26.md)).
- **Safari 26's credential flow** (Safari 26): copied from Safari 27, never captured; detection low (`missingCaptures`).
- **Safari on iOS's 407 flow** (Safari on iOS): the iPhone answered no proxy's 407, even with the Wi-Fi proxy's credentials set; credentials go up front, and `BrowserProxyAuth` is `ErrNotMeasured`; detection low; none planned ([0051](../../docs/decisions/0051-ios-safari-over-the-network.md)).
- **Safari's CONNECTs beside a plain-HTTP page** (Safari; most on iOS): through an HTTP proxy, with the page at `http://`, Safari also sent CONNECTs to the capture host, each on a connection of its own (answered 502 by the capture proxy): one per sample on macOS, four on the iPhone (Safari 26 and 27), heads identical; mimicry sends none; detection low; a capture where the CONNECT is answered, to see what it is for.
- **A link or script navigation from a plain-HTTP page** (all): no profile list measures one (kinds-plain's plain navigations are the typed page and a form POST), so mimicry sends the typed navigation's list: no Referer, Safari's Cookie after Connection, macOS Safari's typed order; detection low to medium; a kinds-plain link navigation ([`proxyPlainGaps`](../../internal/harness/e2e/proxy_test.go)).
- **Safari's plain-HTTP upload without Content-Type** (Safari): Content-Length after Accept, where kinds-plain's POST fetches, all with a Content-Type, have it after Origin as mimicry does; detection low; a kinds-plain fetch of a typeless body (`proxyPlainGaps`).
- **Firefox's last-in-body script over plain HTTP** (Firefox): sent without Priority; kinds-plain's head script went at u=2, the profile's one script list; detection low; a body-script kind (`proxyPlainGaps`).
- **Challenge state per proxy** (all): shared by tunnels and forwarded requests ([INFERENCE]); detection low; a mixed capture.
- **Chrome's preconnects to the proxy**: see Chrome's preconnect above.
- **Ending a tunnel over an HTTP/2 proxy** (Firefox): through an `https://` proxy speaking HTTP/2 (`proxy-https-auth`, Firefox 159 on macOS, every sample), each connection the server sent GOAWAY on was ended by resetting its tunnel's stream to the proxy (RST_STREAM CANCEL right after its last record), with no GOAWAY inside the tunnel, where Firefox answers NO_ERROR on every other connection, an HTTP/1.1 `https://` proxy's tunnels (`proxy-https-h1-auth`) included; `hellogen` leaves the scenarios whose proxy may speak HTTP/2 out of `goawayReply`, and a Firefox profile answers NO_ERROR inside such a tunnel too before the reset; detection low (the server sees one GOAWAY more); a rule for when Firefox skips its reply.
- **Firefox's TLS resumption to an `https://` proxy** (Firefox): over HTTP/1.1, 1–2 of the 11 tunnel connections after the first resumed per sample (the resume page's last, in 7 of 9), the rest full handshakes; a Firefox profile never resumes to the proxy (`proxy.https.resume` false); detection low (the proxy sees it); a rule for which connections resume.
- **Firefox's background connections to an `https://` proxy** (Firefox): its own requests (refused by the capture proxy) send another hello, no session ID and 11 extensions; mimicry makes no such connections; detection none for a caller's traffic.
- **Chrome and Edge's parallel CONNECTs before a 407** (Chrome, Edge): over HTTP/2, 3–4 (Chrome) or 2 (Edge) CONNECTs without credentials before the challenge is answered, its preconnects; mimicry sends one; detection low (the proxy sees it); not planned, as Chrome's preconnect.
- **HTTP/3 through an HTTP proxy** (Chrome, Edge, Firefox; with `Config.ConnectUDPProxy` only): no browser sends HTTP/3 through a configured proxy, so a site that knows the address is a proxy's sees HTTP/3 where a browser would use TCP; the site's QUIC is the profile's (first flights equal through the proxy, `TestQUICInterop` `connect-udp`), but its packets over about 1420 bytes (Chrome's max_udp_payload_size 1472 less the proxy's framing) are dropped on the way, a smaller path MTU than direct. The CONNECT-UDP proxy sees a CONNECT-UDP no browser sends (its fields and order unmeasured), the profile's QUIC with datagrams 64 bytes larger (1314 for Chrome) and no resumption; detection low to medium when the caller opts in, none otherwise; not planned beyond the option ([0066](../../docs/decisions/0066-http3-over-connect-udp.md)).
- **SOCKS4 from the older versions** (Chrome 155, Firefox 158 on macOS and Windows): no `proxy-socks4` capture (not captured, the maintainer's decision, 2026-11-10), so they refuse SOCKS4 (`ErrNotMeasured`); detection none (nothing is sent); none planned, they age out.
- **Safari 26's SOCKS4 is assumed, not captured** (safari-26-macos): it takes Safari 27's `proxy-socks4` and `proxy-socks4a` captures (the maintainer's decision, 2026-11-10; decision 0063); if Safari 26 sends other bytes (another SOCKS4A address, or resolving), the proxy sees Safari 27's; detection by the proxy only, low; a capture at the second Mac (docs/capturing.md, Proxy scenarios).
- **SOCKS4 on the iPhone** (safari-26-ios, safari-27-ios, chrome-157-ios, firefox-159-ios): refused for good (`ErrNotMeasured`; the maintainer's decision, 2026-11-10; [0063](../../docs/decisions/0063-socks4-proxies.md)): iOS offers no SOCKS4 route (the Wi-Fi proxy's Manual setting and configuration profiles are HTTP only, a proxy script's `SOCKS` is SOCKS5 on the networking stack shared with macOS, as measured there, and the hidden SOCKS version key cannot be set on iOS; [INFERENCE] for iOS itself, not tried on a phone), and a SOCKS4 form no iPhone sends would show to the proxy; detection none (nothing is sent); not planned.
- **SOCKS4's address choice** (all): with several IPv4 addresses mimicry sends the first the resolver returns, looking up IPv4 only; which one a browser picks, whether it opens another proxy connection with the next when the proxy refuses, and what Firefox does for a host with IPv6 addresses too (its captures run with `network.dns.disableIPv6`; the IPv4-only lookup is read from Chrome's source), is not measured; detection low; a capture with a multi-address, dual-stack host and a refusing proxy.
- **An IPv4 address through `socks4a://`** (Firefox): sent as plain SOCKS4 (its DSTIP), never captured; detection low; a `proxy-socks4a` capture of an IP-literal URL.
- **TLS resumption through SOCKS4** (Chrome, Firefox, Safari): resumed as directly (as through SOCKS5, `connectNoResume` covers CONNECT tunnels only), not compared over several tunnels; detection low; a SOCKS4 `resume`-style capture.
- **SOCKS4 user ID** (all): browsers send it empty; mimicry sends a SOCKS4 URL's user name there, which no browser does; detection by the proxy only, none planned ([0063](../../docs/decisions/0063-socks4-proxies.md)).
